## 如何阅读本文件

本文件描述 LifeOS 最终要成为的产品，不等于当前版本全部实现。阅读当前开发任务时，应先阅读 [docs/README.md](./README.md)，再结合本文件和对应版本 PRD。

文中使用以下标记：

- `[核心]`：长期产品不可缺少的能力或边界。
- `[扩展]`：完整产品需要，但可以在基础体验稳定后增加。
- `[后续]`：已形成方向，具体交互或优先级仍需未来验证。
- `[待决]`：当前讨论没有足够依据，不能擅自当成定案。

“必须/不得”表示产品约束；“应该/可以”表示目标体验或可选方案。

## 1. 产品定义

### 1.1 一句话定义

LifeOS 是一个以个人真实生活时间线为基础，把行动记录、任务与目标、想法与表达、成长、人物与地点、媒体证据、人生阶段、AI 整理与长期回顾连接起来的个人生活操作系统。

### 1.2 用户要得到的不是“更高分的人生”

LifeOS 的核心价值不是把每一分钟变得高效，而是让用户能：

1. 在当下低成本地留下正在发生的事；
2. 知道今天实际是怎样度过的；
3. 从长期记录中看见兴趣、节奏、目标和生活结构的变化；
4. 记住普通但珍贵的人、事、话和场景；
5. 在没有方向时得到一小步，而不是被强行规划人生；
6. 在未来重新遇见过去，并给过去补充后来才知道的意义。

### 1.3 产品形态

LifeOS 的完整产品由四层组成：

| 层 | 核心问题 | 主要系统 |
|---|---|---|
| 行动 | 我现在做什么？ | Now、Session、Task、Quest、DDL |
| 记录 | 我今天发生了什么？ | Capture、Inbox、Entry、Outcome、Timeline |
| 理解 | 我最近在变什么？ | Review、Growth、Rhythm、Insight、Ask My Life |
| 意义 | 这些过去对我意味着什么？ | Moment、Memory、Echo、Chapter、关系、人生博物馆 |

冒险者协会横跨四层，是帮助用户行动和回顾的表现层，不是 LifeOS 的地基。

## 2. 用户问题与产品目标

### 2.1 核心用户问题

LifeOS 必须持续回应以下问题：

| 编号 | 用户问题 | 产品应提供的方向 |
|---|---|---|
| P-01 | 一天过去了，却不知道自己做了什么 | 低摩擦记录、Session、时间线、每日结算 |
| P-02 | 事情很多，不知道下一步做什么 | 任务分解、最多三项下一步建议、轻量委托 |
| P-03 | 容易忘记任务、承诺和 DDL | Commitment、提醒、最晚开始时间、遗漏恢复 |
| P-04 | 想法出现得快、消失得也快 | 全局 Capture、Spark、Inbox、稍后整理 |
| P-05 | 只知道自己“颓废”，看不见真实生活 | 事实回放、Reality Check、允许休息和空白 |
| P-06 | 想成长，但不知道自己有没有变化 | Growth、Rhythm、结果记录、Then & Now |
| P-07 | 别人说“你变了”，自己不知道变在哪里 | 证据优先的 Insight、时期比较、Ask My Life |
| P-08 | 重要的事后来忘了 | Moment、媒体证据、Memory Anchor、Echo |
| P-09 | 关系和生活阶段会自然变化 | Person、共同时间线、Chapter、用户补充原因 |
| P-10 | 不想把十年人生交给一个服务或模型 | Local-first、隐私空间、AI 权限、可导出与可删除 |

### 2.2 产品使命

> **让一个人能够看见自己正在生活，并为自己的人生留下连续、真实、可理解、可回看的痕迹。**

### 2.3 North Star Metric

首要衡量方向是：

> **用户能清楚知道自己这一天是怎么度过的天数。**

它比任务完成数更接近 LifeOS 的使命。辅助观察指标可以包括：

- 用户完成一次真实日回顾的天数；
- 用户在不完整状态下仍成功留下 Capture 的次数；
- 用户能从记录回到原始证据的比例；
- 用户主动回来查看过去、补充原因或确认 Moment 的次数；
- 用户在一段时间后仍愿意继续使用的连续月份数。

这些指标不得被合并为“人生得分”。

## 3. 完整产品循环

### 3.1 主循环

```text
Chapter / 人生阶段
    ↓
Direction / 方向
    ↓
Goal / 目标
    ↓
Project / 项目
    ↓
Milestone / 里程碑
    ↓
Quest / 当下委托
    ↓
Session / 实际行动
    ↓
Capture、Entry、Outcome、Idea、Journal、Evidence
    ↓
Timeline / 人生时间线
    ↓
Daily、Weekly、Monthly、Yearly、Chapter Review
    ↓
Growth、Rhythm、Insight
    ↓
Moment、Memory、Echo
    ↓
Ask My Life
    ↓
重新理解过去，调整未来方向
```

### 3.2 产品不要求每次循环完整

用户可以只做其中一步：

- 只捕获一句想法，不建立任务；
- 只开始一个 Session，不关联 Goal；
- 只保留一张照片，不写总结；
- 只记录一个普通的休息下午，不产生 Insight；
- 只看时间线，不完成每日结算；
- 只让一段原始语音留在 Inbox，几个月后再整理。

完整循环是长期能力，不是每次使用的表单流程。

## 4. 领域模型与数据语义

完整术语以 [CONTEXT.md](../CONTEXT.md) 为准。以下是 Master PRD 中最重要的产品关系。

### 4.1 五类底层概念

| 概念 | 产品职责 | 典型例子 |
|---|---|---|
| Capture | 保存用户刚刚留下的原始输入 | 一句话、语音、截图、照片、快捷操作 |
| Record | 表示可以进入人生档案的结构化记录 | Task、Session、Journal、Event、Moment |
| Entity | 可被多条记录引用的长期对象 | Person、Place、Goal、Project、Skill、Subject |
| Relation | 说明记录和实体如何相互关联 | 属于项目、发生于地点、由想法发展而来 |
| Insight | 基于证据产生的观察或解释 | 某项活动减少、某段时期可能发生变化 |

### 4.2 原始输入、草稿、定稿

同一条信息可以经历：

```text
Raw Capture / 原始捕获
    ↓
Local Draft / 本地草稿
    ↓
AI Enrichment / AI 丰富建议
    ↓
User Review / 用户审阅
    ↓
Canonical Record / 可引用的定稿记录
```

其中：

- Raw Capture 永远不能被 AI 覆盖；
- Local Draft 可以不完整、过期或由低能力模型生成；
- AI Enrichment 是建议，不是事实；
- Canonical Record 只有在用户确认或规则足够确定时才建立；
- 后续模型可以重新分析旧 Capture，但不得抹去旧版本和来源。

### 4.3 三种信息层级

#### Fact / 事实

由用户明确输入、明确操作或可验证材料直接支持，例如开始/结束时间、原始语句、照片、截图原数值、用户确认的 DDL。

#### User Expression / 用户表达

用户当时的感受、评价、原因和后来补记。例如“今天手很僵”“我后来发现这可能是毕业后最后一次全员在线”。

#### Inference / AI 推断

AI 根据记录提出的分类、趋势、可能原因或变化解释。例如“你可能从长时间低频练习转向短时间高频练习”。它必须附证据和不确定性。

### 4.4 时间证据等级

时间线可以展示不同来源，但必须让用户知道可信度和处理状态：

| 等级 | 来源 | 能否直接成为正式人生事实 |
|---|---|---|
| A | 用户主动开始/结束、明确输入、用户确认 | 可以 |
| B | 用户添加的照片、截图、语音、视频或文件 | 作为证据；含义仍需用户/系统关联 |
| C | 用户开启后产生的设备/应用使用证据 | 默认是 Evidence，不直接等于 Session |
| D | AI 对多个证据的活动猜测 | 默认是 Candidate，需确认 |
| E | 没有足够信息 | 显示为 Unknown，不得硬猜 |

## 5. 信息架构

### 5.1 一级入口

长期产品采用四个主要入口和一个全局入口：

1. **Now / 现在**：当前行动、下一步、今日不可忘事项；
2. **Timeline / 时间线**：按不同尺度查看实际发生的生活；
3. **Journey / 成长与目标**：Chapter、Direction、Goal、Project、Skill、Rhythm 和 Insight；
4. **Archive / 档案馆**：Moment、Echo、People、Places、Ideas、Projects、Chapters、Reviews、媒体和时间胶囊；
5. **+ Capture**：在任何页面快速留下文字、语音、图片、截图、链接、Session 或 Brain Dump。

### 5.2 首页 Now 的三个问题

Now 首屏应按优先级回答：

1. 我现在在做什么？
2. 接下来最适合做哪一小步？
3. 今天有什么不能忘？

首页不应首先展示大段统计或完整任务池。下一步建议默认不超过三项，完整任务池另行查看。

### 5.3 Windows 与移动设备的角色

产品语义必须一致，但交互表面可以不同：

- 移动端优先快速捕获、语音、照片、现场记录、随身时间线；
- Windows 优先键盘快捷捕获、长文本、任务整理、媒体批量处理、复杂回顾和大屏时间线；
- 当前 Session 属于用户而不是某台设备；在设备间移动时，用户看到同一个行动状态；
- 不应把 Windows 做成简单放大的手机页面。

## 6. Capture、Inbox 与火花系统

### 6.1 Capture 的定位 `[核心]`

Capture 是“我要留下点东西”的动作。用户不需要先理解 LifeOS 的内部分类。

支持的入口包括：

- 全局快捷输入；
- 文本、语音和图片；
- 开始/结束 Session；
- Session 内的“发生了什么”；
- Brain Dump / 清空脑袋；
- 截图、战绩、文件或链接；
- 未来可接入的微信、飞书等外部来源。

### 6.2 Inbox 的定位 `[核心]`

Inbox 是“已经留下，但尚未完全整理”的状态，而不是所有数据的垃圾桶。

允许的状态包括：

- 待确认：时间、人物、任务含义不清；
- 待整理：原始语音或长文本尚未拆分；
- 待识别：截图、照片或文件尚未理解；
- 待归属：不知道属于哪个 Project、Goal 或主题；
- 待高级 AI：本地能力不足，等待用户使用外援或云 API；
- 原始保留：用户只想留下，不想整理。

Inbox 必须支持“稍后整理”和“永远不整理”。未整理不等于失败。

### 6.3 多内容捕获

一句输入可以包含多件事。例如“下午和朋友吃饭，聊到毕业后工作，突然觉得不一定想去大城市，明天问一下岗位”可能被建议拆成：

- 一个社交 Session 或补充 Entry；
- 一个 Person/Topic 关联；
- 一条 Journal；
- 一个 Task；
- 一个待用户确认的 Insight 候选。

系统应展示“发现了几项内容”，允许全部保存、逐项确认或保持原文，不得自动把用户表达升级成结论。

### 6.4 Spark / 火花 `[核心]`

火花是低门槛、可暂不整理的 Idea。至少保存发生时间、原始内容和可选上下文：当时正在做什么、在哪里、和谁在一起、可能相关的项目。

火花可以后来：

- 关联已有 Project 或 Goal；
- 合并为同一主题；
- 转为 Task、Journal 或 Moment 候选；
- 被 Ask My Life 找到；
- 因为多年未被处理而通过 Echo 再出现。

## 7. Now、Session 与行动记录

### 7.1 Now `[核心]`

无进行中行动时，Now 提供：

- 快速开始一件事；
- 最近使用的活动快捷入口；
- 快速捕获火花或随手记；
- 今日委托和不可忘事项；
- 最多三项下一步建议。

有进行中行动时，Now 优先显示：

- 行动名称；
- 已持续时间；
- 关联 Task/Project（如有）；
- 一键添加 Entry、语音、图片、火花或 Moment；
- 暂停、结束、切换或标记插曲。

### 7.2 Session 与 Task 的边界 `[核心]`

- Task 表达“准备做什么”；
- Session 表达“现实中做了什么”；
- 一个 Task 可以有多个 Session；
- 一个 Session 可以不属于任何 Task；
- 一个 Session 可以产生多个 Entry 和 Outcome；
- 用户不应为了记录洗澡、发呆、聊天或游戏而先创建任务。

### 7.3 开始、暂停、切换与结束

产品体验目标：开始记录约三秒，结束记录约十秒；详细信息始终可选。

用户应能：

- 通过最近项、自然语言、语音或自定义名称开始；
- 在 Session 中快速写一句“发生了什么”；
- 暂停但不丢失上下文；
- 把短暂行为记为插曲；
- 把较长或意义不同的行为切换成新的主 Session；
- 结束后只补充一句结果，或者直接跳过；
- 事后修改明显错误的开始/结束时间，并保留修改是用户行为而非 AI 事实。

### 7.4 粗记录、细化、合并

LifeOS 允许：

- 先记录“下午在外面”，之后细化为出行、吃饭和聊天；
- 先记录一个大 Session，之后增加子活动；
- 把多个过细 Session 合并为一个更有意义的主活动；
- 保留主活动和 Secondary Activity 的重叠关系，例如通勤中听播客。

时间线应展示层级，而不是强迫用户在每次切换时产生大量碎片。

### 7.5 过程与结果

Session 结束后可以补充：

- 做了什么；
- 分成了哪些阶段；
- 产出了什么；
- 哪些地方遇到困难；
- 主观感受；
- 是否值得成为 Moment 或继续推进。

事实时长和用户表达必须分开。AI 可以整理“前十分钟基本功、后面练《晴天》”，但不能把推测的时长写成事实。

## 8. Task、Commitment、Deadline 与目标体系

### 8.1 任务家族

| 类型 | 含义 | 典型处理 |
|---|---|---|
| Task | 一件可执行事项 | 完成、推迟、拆分、取消、归档 |
| Quest | 面向当下的一小步 Task | 通常当天或短时段完成 |
| Commitment | 对自己或他人有现实后果的事项 | 更可靠的风险提醒和恢复 |
| Deadline | 必须完成或不能再延后的时间点 | 计算风险与最晚开始时间 |
| Event | 已确定在某时刻发生的事件 | 记录发生，不等同于待办 |
| Reminder | 防止遗忘的提醒 | 可独立存在，不必创建 Task |

### 8.2 目标层级

```text
Interest / 兴趣
    ↓（可以长期保持非正式）
Direction / 方向
    ↓
Goal / 目标
    ↓
Project / 项目
    ↓
Milestone / 里程碑
    ↓
Quest / 今日委托
```

这不是强制填写流程。用户可以直接从 Session 开始，也可以从生活中逐渐形成目标。

### 8.3 目标语义

- Interest 表示“我反复在意或接触它”；
- Direction 表示“我想靠近怎样的生活或身份”；
- Goal 表示“我希望达到一个可以阶段性判断的结果”；
- Project 表示“正在推进的一段具体工作”；
- Milestone 表示阶段节点；
- Quest 表示“现在能做的一小步”。

当前主线建议保持一至三条，但这是降低选择成本的建议，不是对用户人生的限制。

### 8.4 形成中的目标

系统可以从重复 Session、火花、Journal、投入和结果中发现 Emerging Goal，例如“你最近不断记录吉他和创作”。它只能提出：

> “这似乎是你最近比较在意的方向，要不要建立一个目标？”

用户拒绝不会扣分，也不会反复骚扰。

### 8.5 任务拆分与最晚开始时间

对于“写论文”“完成产品”这类较大事项，系统应建议改成 Project 或拆成多个 Quest。拆分建议应提供理由、预计耗时和依赖关系，但不能替用户直接修改。

对于有 DDL 的 Commitment，系统应该帮助用户看见：

- 还剩多少时间；
- 估计需要多少行动；
- 最晚什么时候开始仍比较安全；
- 是否已有可用 Session；
- 是否连续推迟；
- 是否需要重新评估范围。

### 8.6 状态与退出

任务/目标至少支持以下语义：

- Planned / 计划中；
- In Progress / 进行中；
- Completed / 已完成；
- Paused / 暂停；
- Deferred / 推迟；
- Abandoned / 主动放弃；
- Archived / 归档；
- Evolved / 演变为其他目标或项目；
- Unknown / 目前无法判断。

放弃、暂停和未完成都是人生历史，不能被“删除后当作没发生”。

### 8.7 提醒与遗漏恢复

提醒分为轻提醒、风险提醒和强提醒，具体强度应受用户设置、事项类型和现实后果影响。强提醒不得自动锁定应用、扣经验或替用户执行。

错过 DDL 后，系统应帮助用户恢复：

- 事实显示“已过期”；
- 询问是继续、缩小范围、重新安排还是放弃；
- 可记录“为什么延误”；
- 保留原 DDL 与后续修改历史。

连续推迟是可供用户理解的行为数据，不是失败惩罚。

## 9. Timeline / 人生时间线

### 9.1 地位

Timeline 是 LifeOS 的长期地基。所有任务、Session、想法、Journal、事件、Moment、媒体关联和用户补记都应能回到时间位置。

### 9.2 时间尺度

支持从近到远的浏览：

1. 具体时刻与 Session 内 Entry；
2. 今日；
3. 本周；
4. 月度；
5. 年度；
6. Chapter；
7. 多年人生。

缩放越远，细节越少，但重大事件、Chapter、Moment、人物、地点、项目、第一次和最后一次保留得越清晰。

### 9.3 显示原则

- Session 是大节点，Entry 是其中的小节点；
- 未知空白可见但不羞辱用户；
- 自动证据、候选和用户确认的记录视觉上可区分；
- 时间线可以显示“今天还有三段待确认”，但不能暗示必须 100% 填满；
- 任何 AI 结论都可以打开“为什么这么说”，回到证据；
- 用户可以按 Life Area、Entity、来源、状态、可见性和时间范围过滤；
- 用户可展开一段时间查看“这段时间发生了什么”。

### 9.4 时间冲突

当多个设备或用户记录产生重叠时，系统不得静默覆盖。应该显示冲突并允许：

- 保留两项；
- 修改时间；
- 合并为主活动与插曲；
- 标记一个为误记；
- 留下“暂时不确定”。

### 9.5 Reality Check

当用户觉得“今天什么都没做”时，LifeOS 可以基于已确认 Session、用户 Capture、可选自动证据和空白时间，给出中性回放：

> “今天已确认的记录包括工作、游戏、通话和吉他；仍有两小时无法确定。”

不得把自动证据直接写成确定事实，也不得评价用户是否“浪费”。

---

## 10. Review / 回顾系统

不同尺度不能只是同一统计图换时间范围。

| 尺度 | 核心问题 | 主要内容 |
|---|---|---|
| Daily | 今天经历了什么？ | 时间线、完成事项、成果、火花、Moment、遗留事项、空白 |
| Weekly | 最近生活节奏怎样？ | Rhythm、投入结构、任务推进、异常变化、轻量提示 |
| Monthly | 什么正在形成变化？ | 趋势、兴趣、技能、目标偏离、可能的变化点 |
| Yearly | 这一年留下了什么？ | 大事件、第一次/最后一次、人物、地点、项目、做到/没做到/放弃 |
| Chapter | 那个阶段的我是什么样？ | 主线、生活结构、关系、转折、开始与结束时的差异 |

### 10.1 Daily Review

每日结算是建议而非义务。理想流程为两至五分钟：

1. 修补或确认时间洞；
2. 处理少量 Inbox；
3. 回答“今天做成了什么”；
4. 回答“今天有没有值得留下的时刻”；
5. 选择需要带到明天的事项；
6. 生成可重新编辑的今日视图。

用户可以跳过，之后再做；当天归档不是锁死，仍可修改。

### 10.2 长期回顾

年度和 Chapter 报告应更像人生叙事而非生产力报告。可以展示统计，但必须结合：

- 重大事件与转折；
- 重要人物和共同经历；
- 主要项目和真实成果；
- 主动放弃或方向改变；
- 照片、截图、语音和原话；
- 当时视角与后来补记。

AI 报告是可重新生成的视图，不是永久真相；新模型可以重新阅读旧资料，但不覆盖原始内容。

---

## 11. Growth、Skill 与 Rhythm

### 11.1 成长档案

Growth 记录“投入—过程—结果—变化”，不只记录时长。领域可以包括：

- 吉他：练习时长、曲目、阶段、录音/视频、困难与突破；
- 游戏：赛季、段位、英雄/位置、战绩、高光、逆风翻盘、低谷与风格变化；
- 工作/学习：项目、产出、技能、结果和反思；
- 运动、创作、阅读或其他用户定义领域。

### 11.2 事实与解释

例如游戏记录可以保存：

- 事实：地图、比分、K/D/A、Rating、角色、日期；
- 用户表达：“第二局很坑，第三局逆风翻了”；
- AI 洞察：“最近三十场主动首杀减少，残局处理可能更保守”。

第三层必须能回到前两层的证据，不能仅凭一句“感觉”生成客观结论。

### 11.3 Rhythm 而不是 Streak

Rhythm 展示过去一段时间活动出现的频率和形态，例如过去 30 天练琴 18 天。它不因某天缺席而归零，不造成断签羞耻，也不要求每天保持。

### 11.4 Then & Now `[扩展]`

允许比较两个时间点或时期的照片、录音、视频、成果和统计，例如第一次弹《晴天》与半年后版本。对比应展示差异并保留原始证据，不将结果压缩为单一成长分数。

---

## 12. Chapter / 人生章节

### 12.1 定义

Chapter 是用户人生中的语境段落，例如“大学最后一年”“第一次独立生活”“探索期”“开始认真做产品以后”。它可以跨越自然年份，也可以没有明确结束日期。

### 12.2 创建和建议

- 用户可以主动创建、命名、调整或结束 Chapter；
- AI 可以根据居住地、工作状态、目标、活动结构和人物变化提出候选；
- AI 不得自动宣布新人生阶段；
- 用户可以拒绝、延后或保持当前 Chapter；
- “探索期/不知道要往哪里走”是合法 Chapter，不是缺陷。

### 12.3 Chapter 回顾

应支持比较 Chapter 开始与结束时的：

- 主线和方向；
- 实际投入结构；
- 目标状态；
- 兴趣、人物、地点和项目；
- 当时的常见表达；
- 第一次、最后一次和转折；
- 用户后来补充的意义。

---

## 13. Moment、Memory、Echo 与 Time Capsule

### 13.1 Moment 的定义

Moment 是现在或未来可能值得再次想起的时刻，不等于重大事件或高成就。

三种来源：

1. 用户当下标记“记住这一刻”；
2. 系统根据表达、成果、人物、媒体和长期影响提出候选；
3. 多年后由于上下文变化，普通记录被发现可能重要。

### 13.2 Moment 的类型

可包括但不限于：第一次、最后一次候选、突破、高光、转折、重逢、结束、普通但珍贵、关系共同节点和项目起点。

系统必须克制推荐，宁可漏掉一些，也不要每天把普通行为都弹成“重要时刻”。

提出 Moment Candidate 时可以参考：用户是否使用“第一次/终于/最后/难得/没想到”等表达，是否关联长期 Goal 或 Milestone，是否有照片/语音/视频，是否关联多个人物，是否明显偏离个人历史，是否有强烈的用户表达，以及这件事后来是否产生持续影响。这些只是候选信号，不应变成一个公开的“重要性分数”。

### 13.3 Moment Cluster

一个 Moment 可以由多个 Record 组成，例如“大学最后一天”包含毕业典礼、合照、最后一顿饭、退宿、离开和当晚的文字。它应保留时间顺序和各项原始证据。

### 13.4 当时视角与后来视角

Moment 可以有多次补记：

- 发生时的原始记录；
- 后来某年用户补充的意义；
- 更久以后再次补充的看法。

补记是新的 User Expression，不能修改当年原话。

### 13.5 Echo / 回响

Echo 把过去带回现在，可由以下触发类型组成：

- 周年或“去年的今天”；
- 很久没做的活动；
- 目前记录中的最后一次出现；
- 第一次开始；
- 曾经的高峰；
- 可能的人生转折；
- 被遗忘的火花；
- 与某个人、地点或 Chapter 的共同记忆。

Echo 的产品约束：

- 每天可为 0–3 条，允许没有回响；
- 不能因“有数据”就强制展示；
- 使用“根据目前保存的记录”“可能”这类边界表达；
- 支持用户说明原因、确认、降低频率、不再主动提起或删除；
- 敏感人物、时期、主题和工作资料可以完全排除；
- 通知预览不得泄露私密照片或原文。

### 13.6 Time Capsule / 时间胶囊 `[扩展]`

用户可以把文字、照片、语音、目标或对未来的猜测封存到某个日期、事件或人生节点。到期后由用户选择是否打开，不应成为强迫提醒。

---

## 14. People 与关系系统

### 14.1 定位

Person 是共同记忆索引，不是 CRM、通讯录替代品或关系绩效表。

可以记录：

- 名称/昵称和用户备注；
- 第一次、最近一次和共同记录；
- 共同 Session、Moment、照片、语音和地点；
- 共同生活时期/关系 Era；
- 用户自己写下的关系备注。

不得默认显示亲密度、重要性分数、好友排行榜或“联系下降 42%”这类价值判断。

### 14.2 人物创建与关系类型

- 从文本中识别人物时，优先形成候选，由用户确认后建立长期 Person；
- 关系类型可选，AI 可以建议但不能替用户决定；
- 不同关系可有少量不同视图，但用户可以自定义；
- 出现次数不等于重要程度。

### 14.3 共同时间线与关系变化

系统可以说：

> “过去 90 天与 A 的共同记录比之前 90 天少。”

不能直接说：

> “你们的关系变差了。”

系统可以询问原因，用户可以补充异地、忙碌、没记录、关系仍然稳定、冲突或其他背景。用户的原因属于 User Expression，应进入关系历史而不是固定人格标签。

### 14.4 关系隐私

每个 Person 或关系时期至少支持：

- 不在普通回顾中主动出现；
- 不做关系分析；
- 不显示照片；
- 不出现在年度报告；
- 只保留但不提醒；
- 封存或彻底删除相关资料。

### 14.5 关系分享

分享“我们的某一年/某段回忆”时，应生成用户审阅过的切片，不能赋予对方浏览完整人生档案的权限。

---

## 15. Place / 地点系统

### 15.1 定位

Place 是人生发生过的舞台，可以是家、学校、公司、城市、旅行地点、常去店铺或用户命名的场所，不只是 GPS 坐标。

### 15.2 关联能力

地点可以连接：

- Session、Event、Moment 和照片；
- 某个 Chapter 的居住/工作语境；
- 人物共同出现；
- 迁移、旅行、搬家和生活结构变化；
- 用户对该地点的备注和后来意义。

精确位置属于高敏感数据。默认只保存用户主动提供或确认的地点层级；自动位置历史必须单独授权、可暂停、可删除和可设置不用于 AI。

---

## 16. Media 与 Evidence

### 16.1 产品定位

照片、截图、语音和视频是记忆证据，不是普通附件。LifeOS 不是手机相册替代品，而是说明“这份媒体发生在我的哪段人生里”。

### 16.2 媒体链路

```text
Raw Media / 原始媒体
    ↓
Evidence / 关联到 Session、Event、Idea 或 Moment
    ↓
Memory Anchor / 某个 Moment 的代表性媒介
    ↓
Echo Material / 未来回响的展示材料
```

### 16.3 媒体类型

- 照片：人物、地点、日常场景、旅行、聚会；
- 截图：游戏战绩、聊天、软件成果、票据、数字生活节点；
- 语音：当时的语气、情绪和原话；
- 视频：技能成长、演奏、运动、旅行、游戏高光和产品演示；
- 文件/链接：项目产出、参考资料或外部证据。

### 16.4 媒体交互

支持：

- 与 Session 自动提出关联候选；
- 用户确认后成为 Evidence；
- 为 Moment 选择封面或 Memory Anchor；
- 在 Echo、年度回顾和分享切片中引用；
- Then & Now 对比；
- 删除媒体但保留事件或 Moment；
- 保留原件、只保留转写或仅保留结构化结果（由用户选择）。

不得默认扫描整个相册。历史相册整理应是用户主动开启的独立功能。

涉及其他人的聊天截图、工作内容、私密倾诉或敏感文件，应默认提高提醒级别，尤其在准备交给外部 AI 时。

---

## 17. Ask My Life / 问我的人生

### 17.1 定位

Ask My Life 不是普通聊天机器人，而是一个以 LifeOS 档案为依据的个人研究入口。它可以长得像对话，但回答必须调用时间线、证据和产品视觉语言。

### 17.2 问题类型

支持：

- 查找第一次、最近一次、原话和相关记录；
- 查找某个主题、人物、地点或项目；
- 比较两个时间段；
- 询问过去几年生活结构或兴趣变化；
- 询问某个目标做到、没做到、放弃和演变；
- 询问“我什么时候可能发生了变化”；
- 请求生成年度、Chapter 或技能报告；
- 纠正 LifeOS 的答案并补充历史。

不同问题应使用不同答案形态：事件卡、原话列表、统计图、时间线、时期对比或叙事分析，不要所有问题都回答成一篇长文章。

### 17.3 证据优先答案

标准回答结构应尽量包括：

1. 直接答案或当前能回答的范围；
2. 事实证据；
3. 用户当时的原话；
4. AI 推断及其不确定性；
5. “为什么这么说？”入口；
6. 回到原始记录/当天时间线/相关 Moment 的入口。

如果资料不足，必须明确说“不知道”“目前没有足够记录”或“现实中可能还有未记录的经历”。

### 17.4 关系问题

可以回答“谁最频繁出现在共同活动记录中”，不能直接回答“谁是你最重要的朋友”，除非用户自己明确这样表达。

### 17.5 用户纠正

当用户说“这不对，我后来还见过他”或“不是没兴趣，是电脑坏了”，系统应允许把纠正保存为新的用户历史补充，并更新相关 Insight 的证据状态，而不是只显示道歉。

### 17.6 权限边界

被封存、被标记为不供 AI 使用、被删除或超出本次上下文范围的数据，Ask My Life 不得偷偷使用。回答中应说明使用了哪些数据范围。

## 18. AI 产品体系

### 18.1 三个角色

| 角色 | 发生时间 | 主要职责 |
|---|---|---|
| 行动助手 | 白天、当下 | 解析输入、拆 Task、推荐下一步 |
| 整理员 | Session 结束、每日/后台 | 整理 Capture、关联、总结、生成候选 |
| 档案研究员 | 长期回顾、Ask My Life | 基于证据回答过去、变化与意义问题 |

### 18.2 AI 层级

产品不绑定某个模型或供应商，长期可有：

1. 无 AI 的规则与事实层；
2. 手机本地小模型；
3. 用户设备上的本地模型；
4. 手动 AI 外援；
5. 用户主动启用的云 API。

核心计时、DDL、统计、数据保存、同步和删除不能依赖任何 AI。

### 18.3 即时 AI 与后台 AI

- 即时 AI：解析“开始练琴”“明天交报告”“记一个想法”，必须快速、可跳过；
- 后台 AI：整理一天、发现趋势、分析游戏风格或寻找 Chapter，允许等待、失败和重试。

### 18.4 AI 外援与 LXF

AI 外援允许用户把选定上下文复制到 ChatGPT、Claude、Gemini、DeepSeek 或其他模型，再把结果粘回 LifeOS。产品应提供：

- 任务模板和内置教程；
- 本次会发送什么的预览；
- 最小必要上下文、标准上下文和用户自选上下文；
- 结构化交换格式 LXF；
- 结果校验、来源 ID 检查和字段权限检查；
- 建议变更预览；
- 全部接受、逐项接受、放弃和重试。

AI 返回的“新增任务、修改 DDL、标记 Moment”都必须先成为建议，不能直接写入档案。

### 18.5 事实保护

AI 可以帮助生成：

- 标题、摘要、标签、Life Area；
- Session 分段与结果候选；
- 主题、项目和实体关联；
- 高光、低谷、可能的趋势；
- 下一步建议。

AI 不得擅自修改：

- 原始文字、语音、照片、截图和视频；
- 用户明确记录的时间、时长、DDL 和数值；
- 用户确认的事件和状态；
- 已删除或禁止读取的内容。

### 18.6 自动记录与候选

如果用户主动开启应用使用、设备状态、媒体关联或位置辅助：

- 自动观察先成为 Evidence；
- AI 分类先成为 Candidate；
- 高置信度且低敏感的信息可由用户单独设置自动确认；
- 敏感领域不得自动推断关系、冲突、心理状态或人生原因；
- 用户可以设置某个 App、地点、时间段或整小时“不观察”；
- 原始数字足迹可以短期保存，确认或过期后按设置清理；
- 删除证据后，相关 Insight 不得继续把它当有效依据。

长期可提供三档观察偏好：

- **轻量辅助**：只使用用户主动 Session、Task 和手动输入；
- **标准辅助**：增加用户允许的应用使用概况、日历和媒体关联，作为推荐默认方向；
- **深度记录**：用户主动允许更详细的应用活动、设备状态、位置和系统事件，明确标识为量化自我模式。

三档都必须能随时暂停，并提供按 App、地点、主题和时间段的“不要观察”设置。标准辅助不是默认同意深度记录。

### 18.7 自动提醒不等于自动干预

LifeOS 可以识别“已经连续使用短视频较久”“某个 Commitment 即将有风险”并给出用户可关闭的提醒；核心产品不得自动关闭 App、锁屏、阻止打开、扣经验或替用户执行控制动作。提醒的目的应是把选择权交还用户，而不是接管用户生活。

### 18.8 AI 失败时的体验

模型不可用、网络断开、格式错误或结果质量不足时：

- 原始 Capture 已经保存；
- 用户可以稍后再处理；
- 可以换设备、换模型或使用 AI 外援；
- 不能因为 AI 失败而阻塞开始/结束 Session、查看时间线或完成任务。

## 19. Privacy、Space 与数据控制

### 19.1 六条隐私原则

1. 默认私有，而不是默认共享；
2. 本地优先，而不是云端优先；
3. 数据存在不等于授权 AI 阅读；
4. 分享的是用户选择的人生切片，不是人生数据库访问权；
5. 用户有权保留过去，也有权要求系统不主动提起；
6. 用户可以真正删除自己的数据。

### 19.2 Space 与 Visibility

Space 是一组数据的默认边界，长期可包括：

- Personal / 个人；
- Private / 私密；
- Work / 工作；
- Shared / 可分享。

Visibility 是单条记录的可见性。默认均为私人。Space 不替代逐条权限，逐条权限也不应迫使用户每次输入都做复杂选择。

### 19.3 AI 权限

“数据保存在 LifeOS”与“允许外部 AI 读取”必须是两个独立决定。生成 AI 外援或云分析前，应显示：

- 将发送的时间统计、任务、Session、媒体、原话和地点层级；
- 不发送的日记、关系、工作、精确位置或原始媒体；
- 数据将发送到本地模型、配对电脑还是第三方服务；
- 本次授权是否仅一次、是否可撤销。

私密空间和工作空间默认禁止外部 AI，用户单次明确授权后才可例外。

### 19.4 Vault 与主动不回顾

Vault 用于保存但低曝光的内容。封存后默认不出现在普通搜索、Echo、年度回顾、分享和 AI 分析中，除非用户主动进入并授权。

“不再主动提起”不等于删除。它适用于人物、主题、时期和 Chapter。

### 19.5 删除语义

用户应能区分：

- 隐藏：暂时不主动展示；
- 归档：退出当前生活但保留历史；
- 移除媒体：保留事件/文字，删除照片、语音或视频；
- 删除云端副本：本地仍保留；
- 彻底删除：从有效档案、统计、AI、Echo 和 Insight 中移除。

彻底删除后，相关 AI 洞察若依赖被删除证据，也必须失效或重新生成。

### 19.6 其他人的隐私

用户写下的内容可能包含朋友、家人、对象、同事的隐私。导入聊天截图、工作资料或私密倾诉时，应提醒用户谨慎交给外部 AI，并支持仅本地保存、仅保留结构化结果或手动处理。

## 20. Local-first、离线与同步

### 20.1 三种使用模式

| 模式 | 网络 | 服务端 | 产品价值 |
|---|---:|---:|---|
| Local | 无网络也可 | 不需要 | 单设备记录、查看和管理 |
| Peer Sync | 同一局域网或设备热点 | 不需要 | 手机与 Windows 交换变化 |
| Cloud Sync | 可联网 | 可选 | 异地增量同步、备份和大媒体存储 |

### 20.2 断网能力

断网时必须仍然能够：

- 开始/暂停/结束 Session；
- 创建、完成和推迟 Task；
- 快速 Capture 和保存媒体；
- 查看本地 Timeline；
- 完成基础统计和每日结算；
- 把记录留在 Inbox 等待后续整理；
- 查看和修改隐私设置。

AI、远程回顾和云备份失败不应影响上述能力。

### 20.3 局域网优先

手机和 Windows 在同一 Wi-Fi 或手机热点下可以发现并配对，通过用户确认的设备关系交换变化。产品体验应体现：

- 当前行动属于用户，不属于某台设备；
- 手机上开始、电脑上继续、电脑上结束，形成一条 Session；
- 只同步用户允许的 Space、媒体和 AI 数据范围；
- 用户可以暂停、断开、撤销配对。

### 20.4 冲突处理

两台设备都离线工作时，系统可能出现时间重叠、同一任务不同状态或同一 Capture 多个草稿。产品必须：

- 保留双方变化；
- 展示冲突原因和时间；
- 提供合并、选择、保留两项、标记误记或暂不处理；
- 不静默以最新设备覆盖全部人生记录。

### 20.5 云服务的角色

云端用于异地同步、备份和大文件，并不是核心运行条件。长期应允许用户了解、导出或选择备份位置；可选方向包括官方云、NAS、WebDAV 或自建服务，但具体方案不在本 PRD 锁定。

## 21. 冒险者协会与游戏化

### 21.1 定位

Adventurer Guild 是降低行动负担、提供仪式感和陪伴感的外壳。真实人生优先，游戏数值不能反过来定义用户。

### 21.2 允许的游戏化

- 轻量总等级，表示使用和经历的积累，不是人生质量；
- 领域等级与真实数据并列，例如累计时长、次数、曲目和最近一次；
- 经验来自行动、探索、成果、重要经历和记录，不只来自生产力；
- 轻量金币，用于主题、头像框、房间摆件或收藏品；
- 角色房间/人生博物馆，展示毕业、项目、旅行、技能、关系和 Moment；
- 协会接待员负责任务建议、风险提醒、每日结算和回响；
- Rhythm 代替 Streak，展示规律而不制造断签焦虑。

### 21.3 禁止的游戏化

- 不扣经验、不扣金币、不降级、不破坏连胜；
- 不把游戏、休息、社交自动判定为负面；
- 不用人生总分、人格分数或表现等级审判用户；
- 不用奖励把用户逼向单一生活方式；
- 不要求每天完成游戏化流程才能保持档案完整。

### 21.4 协会接待员的语气

接待员大多数时候应安静。只有用户需要、存在真实风险、出现值得回顾的内容或用户主动打开时才出现。它的语言应具体、中性、可行动，并提供“今天算了”“以后再说”“不再提醒”等退出方式。

---

## 22. 分享与输出

### 22.1 分享原则

默认不提供他人浏览完整 Timeline 的权限。分享必须是用户选定范围、对象、媒体、原话和时间段后生成的副本/切片。

### 22.2 可分享的故事

- 某一年的个人回顾；
- 我和某人的共同回忆；
- 某个项目从想法到完成的轨迹；
- 某项技能的 Then & Now；
- 某段旅行或 Chapter；
- 用户明确选择的 Moment 集合。

分享前必须预览并能移除敏感内容。导出的内容应与原始档案保持边界，后续撤回分享副本不等于自动删除对方已经保存的副本。

---

## 23. 核心产品状态与异常边界

LifeOS 应把以下情况视为正常，而不是错误用户：

- 用户没有明确目标；
- 用户只想休息、娱乐或发呆；
- 用户开始了 Session 却忘记结束；
- 用户有多个重叠活动；
- 用户三个月没有使用；
- 用户只留下原始语音或截图；
- AI 误分类或格式失败；
- 设备长期离线；
- 时间线存在未知空白；
- 任务主动放弃；
- 用户不想回顾某个人或时期；
- 设备同步发生冲突；
- 用户认为系统的 Insight 错了。

对应的产品行为应是保留、解释、让用户选择和支持恢复，而不是惩罚、覆盖或伪造完整性。

## 24. 长期需求分层

### 24.1 基础连续性（必须先稳定）

- Capture、Inbox、Session、Task、DDL、Timeline；
- 每日结算和基础 Review；
- 原始记录保留与可回到证据；
- 离线使用与设备间同步；
- 基本隐私边界；
- 简单 AI 整理与手动外援。

### 24.2 结构化成长

- Goal/Project/Milestone/Quest 层级；
- Skill、Rhythm、Outcome；
- Moment、媒体上下文、Then & Now；
- Chapter 与年度/阶段回顾；
- Relationship 和 Place；
- 可解释的 Insight。

### 24.3 长期人生档案

- Echo 及敏感回顾控制；
- Ask My Life；
- 多年变化和时期比较；
- 自动证据与候选 Session；
- Time Capsule；
- 分享切片与人生博物馆；
- 更丰富的本地/云 AI 协同。

### 24.4 可探索但不得默认扩张

- 微信/飞书等外部来源；
- 完整游戏数据和视觉分析；
- 精确位置长期观察；
- 更复杂的 RPG 职业、装备和收藏；
- 蓝牙同步；
- 社交网络式主页或关系浏览。

## 25. Master PRD 的产品验收原则

当一个长期版本声称符合 Master PRD 时，至少应满足：

1. 用户能在不整理完美的情况下留下真实记录；
2. 用户能把当天记录回到 Timeline，并看见未知空白；
3. Task、Session、Capture、Moment 和 Insight 的边界没有被混成一个对象；
4. AI 的每个重要判断都可以解释来源和不确定性；
5. 原始信息没有被 AI 摘要覆盖；
6. 失败、放弃、休息、娱乐和离开使用都不会触发羞辱或数值惩罚；
7. 用户能控制私密内容、外部 AI、回响、分享和删除；
8. 无网络、无模型或无服务器时，核心记录仍可用；
9. 用户能够从具体的一天一路回到 Chapter、Moment 和长期人生变化；
10. 任何新增功能都能说明它如何增强“看见自己确实活过”。

---

## 26. 与版本 PRD 的关系

Master PRD 描述最终产品形态。版本 PRD 可以裁剪范围，但必须明确写出：

- 本版本实现了哪些 Master Requirement；
- 哪些暂不实现；
- 暂不实现是否需要为未来保留入口、数据或边界；
- 当前简化是否会改变长期语义；
- 若出现冲突，是否需要进入 Decision Log 和上位文档修订流程。
