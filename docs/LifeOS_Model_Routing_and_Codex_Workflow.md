# LifeOS 模型路由与 Codex 协作工作流

> 文档类型：产品协作与模型路由规范  
> 版本：v1.0  
> 状态：Draft / 可执行基线  
> 适用范围：LifeOS 的产品讨论、需求分析、设计、实现、验证、审查与发布协作  
> 本文档不包含：业务实现代码、数据库实现、接口实现或具体技术框架方案

---

## 0. 文档定位

LifeOS 不应把所有工作都交给同一个模型，也不应把“模型更强”误认为“模型一定更适合”。本文件把模型选择、Agent 分工、交接方式和升级规则固定成一套可复盘的协作流程。

本文件解决的是：

- 当前任务应该由哪个角色主导；
- 哪些工作可以并行，哪些工作必须串行；
- 什么时候可以让较低成本的模型继续处理；
- 什么时候必须升级到更强的推理与审查角色；
- 需求不完整时，执行 Agent 能做什么、不能做什么；
- 如何区分“完成了代码工作”和“产品上确实可以接受”。

本文件不能改变 LifeOS 的产品定义。它是协作层规范，产品语义仍由以下文档决定：

> Product Constitution > Master PRD > 当前 Version PRD > 其他产品/设计文档

其中，`Decision Log` 用来解释已经做过的关键选择；它不能在没有明确记录的情况下推翻更高层级的产品定义。本文件也不能覆盖以上任何文档。

## 0.1 规范用词

- **必须**：不满足时不得进入下一阶段。
- **应该**：默认遵守；确有原因时可以偏离，但要在交接记录中说明。
- **可以**：允许采用，不构成强制要求。
- **执行 Agent**：负责调查、修改、测试或其他具体产出的 Agent。
- **决策 Agent**：负责解释产品意图、处理取舍和确认边界的 Agent，默认由 Sol 主导。
- **审查 Agent**：不负责制造被审查的主要产出，而是独立判断其是否符合要求。

## 1. 总体协作原则

### 1.1 路由的目标是“足够强且足够合适”

模型路由使用能够满足质量标准的最低复杂度角色，而不是所有任务默认使用最高配置：

- 低风险、边界明确、重复度高的工作优先交给 Luna；
- 设计已确定、范围清楚、需要真实修改的主力工作优先交给 Terra；
- 有重大歧义、跨模块影响、不可逆风险或产品方向取舍的工作由 Sol 主导；
- 任务在执行中变得更复杂时，必须升级，而不能为了节省成本继续猜测。

### 1.2 先判断任务，再选择模型

不得仅根据“这看起来像前端任务”或“这只是文档任务”来选模型。同一类工作可能有完全不同的路由：

- 按既定规则批量改名，是 Luna 适合的机械任务；
- 改名会影响 LifeOS 核心对象含义，则需要 Sol 先确认语义，再由 Terra 或 Luna 执行；
- 重新设计 Timeline 的叙事结构，是 Sol 的产品决策工作；
- 按已经确认的页面方案完成组件，是 Terra 的实现工作。

### 1.3 产品真相、原始记录和协作判断必须分开

模型可以提出建议、总结事实和发现风险，但不能把推测伪装成产品决定。任何 Agent 都必须区分：

1. 文档已经明确的事实；
2. 用户已经确认的决定；
3. 当前 Agent 的推断或建议；
4. 尚未解决的问题。

只有第 1、2 类可以直接作为已批准约束使用。第 3 类必须标注为建议，第 4 类必须进入上报或询问流程。

## 2. 三种模型角色

### 2.1 Sol：Lead / 架构与高风险推理 / 最终审查

Sol 是 LifeOS 的项目负责人和质量闸门，不是默认承担所有机械实现的“万能工”。

Sol 负责：

- 阅读并解释 Product Constitution、Master PRD、当前 Version PRD；
- 判断需求是否与产品使命、长期领域模型和当前版本范围一致；
- 处理多个合理方案之间的产品取舍；
- 设计跨模块的行为边界、交互逻辑和验收标准；
- 处理数据模型重大变化、数据迁移、同步冲突、隐私权限和 AI 数据边界；
- 判断一个问题是局部缺陷，还是会导致产品方向偏移的系统性问题；
- 为 Terra 的实现提供清晰、可审查的决策包；
- 在高风险任务中担任最终 Reviewer；
- 对发布前的产品一致性、隐私、数据安全和不可逆行为做最终判断。

Sol 不应被用于：

- 已经确定模式的批量格式修改；
- 简单的仓库搜索和文件索引；
- 没有语义变化的重复测试骨架；
- 可以由明确验收标准判断的机械校验。

### 2.2 Terra：主力实现模型

Terra 是 LifeOS 的默认主力执行者，负责把已经确认的产品决策转化为可运行、可测试、可审查的工作成果。

Terra 负责：

- 实现范围明确的页面、交互、状态和数据流；
- 完成普通的跨文件修改、组件整理和模块内重构；
- 根据批准的验收标准编写有意义的测试；
- 修复有明确复现步骤和预期行为的缺陷；
- 承担已经由 Sol 定义边界的同步、离线、AI 调用和媒体流程实现；
- 根据审查意见进行返工并保持改动范围可控；
- 在实现过程中主动报告新发现的歧义、风险和范围膨胀。

Terra 不得：

- 自行决定未定义的产品语义；
- 为了让测试通过而改变原始记录、隐私边界或用户可见行为；
- 把“实现起来最方便”的方案当成产品决定；
- 在没有得到升级或确认前扩大 P0 范围。

### 2.3 Luna：仓库调查、低风险高重复工作与基础验证

Luna 是侦察兵和机械验证者，适合快速建立事实面、处理高重复度工作，并提供不带产品臆测的验证结果。

Luna 负责：

- 搜索仓库、建立文件索引、查找引用关系和影响范围；
- 汇总已有组件、页面、测试、文档和约定；
- 对重复模式执行低风险、边界明确的批量修改；
- 生成基础测试样例、测试矩阵、链接检查和格式检查结果；
- 执行 lint、类型检查、静态检查或其他机械验证；
- 分析日志、整理失败项和标记可能相关的文件；
- 检查实现是否覆盖已列出的清单，但不替代产品语义审查。

Luna 不得：

- 在需求缺口处自行补写产品规则；
- 解释或重定义 Goal、Task、Session、Moment、Echo 等核心对象的含义；
- 处理隐私、授权、数据删除、同步冲突等高风险取舍；
- 以“搜索结果没有发现问题”代替真正的产品验收；
- 无批准地同时修改多个 Agent 共同拥有的关键文件。

### 2.4 角色与平台模型名称的关系

Sol、Terra、Luna 首先是 LifeOS 的协作角色，其次才是对当前模型配置的映射。模型供应商的名称、可用模型、推理档位和价格可能变化，因此每次启动项目时都应确认当前环境是否仍提供相应能力。

截至本文件编写时，OpenAI 官方模型指南将 GPT-5.6 家族区分为面向复杂生产工作的 `gpt-5.6-sol`、平衡能力与成本的 `gpt-5.6-terra`，以及适合高吞吐、成本敏感任务的 `gpt-5.6-luna`；官方同时强调模型选择应根据具体工作负载和代表性任务验证，而不能只看名称。详见 [OpenAI 官方模型指南](https://developers.openai.com/api/docs/guides/latest-model)。

本项目的规则是：

- 平台模型名改变时，先更新角色映射和测量记录，不改变 LifeOS 的产品原则；
- 不把“平台可能提供自动路由”当成项目已经具备自动路由；
- 如果实际可用模型与角色名称不一致，应按能力和验证结果重新映射，并在 `Decision Log` 记录原因。

## 3. Lead、Implementer、Reviewer 的职责分离

### 3.1 三种职责

| 职责 | 主要问题 | 默认角色 | 不能替代的职责 |
|---|---|---|---|
| Lead / 决策者 | 这件事应该做成什么、边界在哪里 | Sol | 不能把未确认的决定藏在实现里 |
| Implementer / 执行者 | 如何在已确认边界内完成工作 | Terra；机械工作可由 Luna | 不能自行发明产品语义 |
| Reviewer / 审查者 | 产出是否符合文档、验收和风险要求 | Sol；机械检查可由 Luna 辅助 | 不能只因为代码能运行就判定通过 |

### 3.2 审查独立性规则

- 普通、低风险、可机械判断的修改，可以由 Luna 生成并完成基础验证；
- Terra 实现的普通功能，至少应由 Luna 完成机械检查，必要时由 Terra 之外的上下文进行审查；
- 涉及产品语义、核心对象、隐私、同步、AI 权限、数据迁移或发布决策时，Reviewer 必须与主要 Implementer 分离；
- 高风险任务的最终审查默认由 Sol 完成；
- 同一个 Agent 可以在不同阶段扮演不同职责，但不能把自己上一阶段的判断当成独立审查证据；
- Reviewer 应引用需求、验收标准或决策记录，指出证据和缺口，不得静默替换产品决定。

### 3.3 审查结果只能有四种状态

1. **Pass**：证据充分，可以进入下一阶段；
2. **Changes Requested**：方向正确，但需要明确返工；
3. **Needs Decision**：发现产品或范围问题，必须回到 Lead；
4. **Blocked**：环境、依赖、权限或外部条件阻断，暂时不能可靠判断。

## 4. 任务路由的五个指标

每项工作在启动时都要用以下五个指标做简短判断。指标不是为了制造复杂评分，而是为了避免“看见任务类别就盲选模型”。可以使用低、中、高三档；如果一个高风险信号已经足够触发升级，不必为了凑分再计算其他项。

### 4.1 Ambiguity：歧义度

| 等级 | 判断标准 | 典型处理 |
|---|---|---|
| 低 | 文档、验收标准和输入都明确，只有表达差异 | Luna 或 Terra |
| 中 | 有少量未写清楚的边界，但不影响主要方向 | Terra 先列出假设；必要时请 Sol 确认 |
| 高 | 多种产品行为都合理，或文档之间出现冲突 | 立即由 Sol 解释、决策或上报 |

“我觉得用户大概会这样用”不能把高歧义降成低歧义。高歧义的重点不是快速猜一个答案，而是把问题显式化。

### 4.2 Scope：影响范围

| 等级 | 判断标准 | 典型处理 |
|---|---|---|
| 局部 | 单文件或一个边界清楚的模块，行为不外溢 | Luna 或 Terra |
| 模块 | 影响一个完整领域或多个相关文件 | Terra 主导，Sol 做边界审查 |
| 跨模块 | 影响多个领域、共享对象、导航、同步或长期数据 | Sol 先定方案，Terra 分段实现 |

范围按行为影响判断，不按文件数量判断。改一个共享对象定义，可能比改十个展示文件更大。

### 4.3 Risk：失败代价

| 等级 | 判断标准 | 典型处理 |
|---|---|---|
| 低 | 可回滚、无敏感数据、不会改变产品语义 | Luna 或 Terra |
| 中 | 用户可见、可能影响既有流程，但有清晰回滚方案 | Terra，配合独立验证 |
| 高 | 隐私、授权、数据丢失、同步冲突、不可逆迁移、核心体验偏移或发布影响 | Sol 必须参与并做最终审查 |

LifeOS 的“真实记录不可被 AI 覆盖”“默认隐私”“允许空白”等边界属于高风险产品约束，不因实现工作看起来简单而降级。

### 4.4 Reasoning：推理复杂度

| 等级 | 判断标准 | 典型处理 |
|---|---|---|
| 低 | 搜索、整理、格式化、枚举、重复验证 | Luna |
| 中 | 局部业务逻辑、常规状态变化、已确定方案的组合 | Terra |
| 高 | 架构取舍、长期演化、跨模块一致性、复杂因果或高不确定性 | Sol 主导 |

### 4.5 Repetition：重复度

| 等级 | 判断标准 | 典型处理 |
|---|---|---|
| 低 | 每次都需要重新理解上下文和做判断 | Sol 或 Terra |
| 中 | 有稳定模式，但仍需要局部判断 | Terra |
| 高 | 输入、规则和输出结构都稳定，可以批量执行和校验 | Luna 优先 |

重复度只能降低机械工作成本，不能覆盖歧义和风险。高重复度的隐私权限修改仍然要由 Sol 先定义规则。

### 4.6 组合路由规则

- **任一指标为高歧义或高风险**：Sol 至少负责决策与闸门；实现可以再交给 Terra。
- **范围为跨模块且推理为中或高**：先由 Sol 画出边界，再交给 Terra 分段实现。
- **五项均低，且重复度高**：Luna 可以主导，并输出可复核的机械验证证据。
- **歧义低、风险低、方案已批准，但需要真实修改**：Terra 默认主导。
- **任务在执行中出现指标升高**：按升级规则重新路由，不能沿用初始模型。
- **任务同时包含决策和执行**：拆成 Lead/Implementer/Reviewer 三个职责，不让一个执行 Agent 默默承担全部判断。

## 5. 需求缺口与“禁止擅自决定”闸门

### 5.1 任何执行前的必读顺序

完整的任务启动顺序、授权判断、停问条件、测试、Definition of Done 和结果汇报由 [`Codex_Operating_Manual.md`](Codex_Operating_Manual.md) 统一规定。本文件在其中作为模型与协作路由阶段的专门规则被读取，不再另起一套与 Operating Manual 冲突的流程。

按 Operating Manual 启动时，最小顺序是：

1. [`README.md`](README.md)：阅读顺序、权威层级和项目使用方式；
2. [`LifeOS_Product_Constitution.md`](LifeOS_Product_Constitution.md)：使命、不可违背的原则和产品边界；
3. 当前版本 PRD，例如 [`LifeOS_V0.1_PRD.md`](LifeOS_V0.1_PRD.md)：本次真正允许实现的版本范围；
4. 与任务相关的 [`LifeOS_Master_PRD_v1.0.md`](LifeOS_Master_PRD_v1.0.md) 章节：完整产品形态、领域模型和长期闭环；
5. [`LifeOS_Decision_Log.md`](LifeOS_Decision_Log.md)：涉及已有取舍、冲突或未决问题时查阅；
6. 本文件：模型选择、Agent 协作、交接和升级规则；
7. [`Codex_Operating_Manual.md`](Codex_Operating_Manual.md)：执行本手册规定的任务流程、验证和汇报。

任务涉及对象、状态或术语时，另外查阅 [`../CONTEXT.md`](../CONTEXT.md)。纯搜索、格式检查或已批准的批量机械任务可以缩短阅读，但一旦发现语义变化、共享对象、隐私、同步或范围问题，必须回到完整顺序。

### 5.2 需求缺口处理流程

执行 Agent 发现需求没有答案时，必须依次完成：

1. 回看 Product Constitution，确认是否存在长期原则；
2. 回看 Master PRD，确认是否已经定义完整产品行为；
3. 回看当前 Version PRD，确认是“最终有、当前暂不做”，还是当前版本遗漏；
4. 回看 Decision Log，确认是否已有历史决定、前提或明确待定项；
5. 将问题分类为“已有答案”“当前版本明确排除”“文档冲突”“真正缺失”；
6. 若仍无答案，停止相关语义实现，提交上报或询问。

上报内容至少包括：

- 问题的精确表述；
- 涉及的对象、页面或流程；
- 已经查阅的文档和相关段落；
- 当前能确认的事实；
- 可能方案及其取舍；
- 不做决定会阻断哪一部分工作；
- 建议由谁确认，以及确认后需要更新哪份文档。

执行 Agent 可以提供建议，但不能把建议直接写成产品行为。只有用户、产品负责人或被明确授权的 Sol 完成确认后，才能更新决策并继续实现。

### 5.3 必须上报的典型问题

- 一个 Capture 是否应自动成为正式 Event、Journal 或 Moment；
- Session 与 Task 的边界是否被新功能改变；
- AI 是否可以读取某个私密 Space、媒体或关系记录；
- 同步冲突时是否允许覆盖用户原始记录；
- 删除、合并、迁移是否会导致历史证据丢失；
- 某个长期 Master 能力是否要提前进入 V0.1 的 P0；
- 新的游戏化分值是否会把 LifeOS 变成自律惩罚器；
- 新页面是否会改变“真实人生大于数值”的核心体验。

### 5.4 明确的停止条件

出现以下情况时，执行 Agent 必须暂停相关部分并标记 `Needs Decision`：

- 需要编造一个文档没有定义的状态、字段含义或用户可见规则；
- 两份同等级文档对同一行为有冲突；
- 继续工作会扩大版本范围；
- 继续工作可能覆盖、删除、泄露或重新解释原始生活记录；
- Reviewer 与 Implementer 对产品预期理解不一致；
- 机械检查通过，但产品行为是否正确仍无法判断。

## 6. 推荐主流程

LifeOS 的默认协作顺序是：

> **Luna 侦察 → Sol 关键决策 → Terra 主实现 → Luna 机械验证 → Sol 最终审查**

这五步不是必须为每个一行文字修改都完整执行，但任何跨模块、用户可见或进入版本交付的工作都应遵守。

### 6.1 第一步：Luna 侦察

目标是建立事实面，不做产品拍板。

Luna 应输出：

- 相关文档、页面、模块和测试的清单；
- 已存在的对象、状态、命名和调用关系；
- 预计影响范围；
- 已知约束和潜在冲突；
- 仍然未知的问题；
- 可由机械规则验证的项目。

退出条件：事实清单足以让 Sol 判断范围，或者明确指出“信息不足，需要用户补充”。

### 6.2 第二步：Sol 关键决策

Sol 结合侦察结果和产品文档，确定：

- 本次任务的目标和非目标；
- 采用的产品语义和边界；
- 哪些内容属于当前版本，哪些明确不做；
- 页面、流程、状态和验收标准；
- 隐私、同步、AI 或数据风险的处理方式；
- Terra 可以直接执行的部分；
- 需要在实现前继续询问的部分。

退出条件：实现 Agent 不需要自行猜测核心产品行为，并且每项主要产出都有可检查的验收标准。

### 6.3 第三步：Terra 主实现

Terra 只在已批准范围内工作：

- 按决策包逐项实现；
- 保留原始记录和既有隐私边界；
- 遇到新歧义时停在边界处，不向前猜测；
- 将超出范围的发现单独列出，不顺手扩展；
- 提供变更摘要、已完成项、未完成项和自测证据。

退出条件：批准范围内的实现完成，且所有未完成项、假设和阻断因素均已显式记录。

### 6.4 第四步：Luna 机械验证

Luna 根据决策包和变更清单执行：

- 文件和引用完整性检查；
- 类型、格式、lint、构建或基础测试检查；
- 路由、链接、状态枚举和重复模式检查；
- 验收清单的逐项覆盖检查；
- 已知异常和失败日志的整理。

Luna 可以指出“证据缺失”，但不能仅凭机械检查给出产品语义通过结论。

退出条件：机械检查结果清晰，失败项有分类，剩余风险已经交给正确的 Reviewer。

### 6.5 第五步：Sol 最终审查

Sol 重点审查：

- 是否符合 Product Constitution 和 Master PRD；
- 是否把当前 Version PRD 的范围误扩展到未来能力；
- 用户可见行为、空白状态和异常状态是否合理；
- 原始记录是否被覆盖、隐藏或错误推断；
- 隐私、AI 读取权限、同步冲突和数据丢失风险；
- 验收证据是否足够，而不是只看“测试通过”；
- 返工成本是否低于现在解决问题的成本；
- 是否需要新增或更新 Decision Log。

最终只能输出 `Pass`、`Changes Requested`、`Needs Decision` 或 `Blocked`。只有 `Pass` 才能进入发布或下一项依赖工作。

### 6.6 流程可以回环

- Luna 侦察发现语义冲突：回到 Sol；
- Sol 发现 Version PRD 不足：回到需求确认，并更新文档；
- Terra 实现发现共享对象影响扩大：回到 Sol 重新划分范围；
- Luna 验证发现异常涉及核心行为：跳过继续机械修改，交给 Sol；
- Sol 最终审查发现方向正确但细节不符：回到 Terra，返工后再次验证。

## 7. 自动升级与降级规则

### 7.1 立即升级到 Sol 的信号

出现任一项时，不等待失败次数，直接升级：

- 需求、产品文档或历史决策之间出现冲突；
- 需要选择两个以上合理的产品行为；
- 影响 Product Constitution、Master PRD 或当前版本边界；
- 涉及隐私、授权、AI 数据范围、原始记录、删除、合并或数据迁移；
- 涉及同步冲突、离线合并、跨设备一致性或不可逆写入；
- 影响多个核心领域或共享对象；
- 可能改变用户对 Now、Timeline、Journey、Archive、Echo 或 Ask My Life 的基本理解；
- Reviewer 无法仅凭验收标准判断正确性；
- 用户可见的错误会长期污染生活档案；
- 需要决定是否把未来能力提前纳入当前版本。

升级时可以只把“决策片段”交给 Sol，不必把所有机械工作重新交给 Sol。

### 7.2 从 Luna 升级到 Terra

出现以下情况时，Luna 不应继续承担主实现：

- 修改不再是稳定模式的重复应用；
- 需要理解局部业务状态或多个组件之间的行为；
- 需要编写有意义的测试，而不是只生成样例；
- 一个机械变更引起了局部回归，需要判断修复方式；
- 需要在多个可行实现之间作局部技术取舍；
- 批量操作中出现例外项，且例外项有明确但非机械的规则。

### 7.3 从 Terra 升级到 Sol

出现以下情况时，Terra 必须停止相关实现并升级：

- 实现过程中发现原需求有多个解释；
- 影响范围从模块内扩大到跨模块；
- 为通过测试而需要改变产品语义；
- 连续两次返工仍不能达到同一验收标准；
- 发现可能的数据丢失、越权读取、错误归档或错误同步；
- 设计方案与 Constitution、Master PRD 或 Decision Log 不一致；
- Implementer 与 Reviewer 对预期行为产生实质分歧。

“连续两次”只适用于普通失败；高风险信号仍然立即升级。

### 7.4 允许降级的条件

只有同时满足以下条件时，才允许从 Sol/Terra 降到较低角色：

- 产品决策已经写清楚并被确认；
- 当前工作不再包含开放性语义判断；
- 范围、输入、输出和验收标准稳定；
- 风险可回滚，且没有新的隐私、同步或数据完整性问题；
- 降级不会把审查职责一并删除。

例如，Sol 已经决定“哪些条目进入 Timeline”，之后按清单检查链接可以降为 Luna；但“什么算值得进入 Timeline”仍然不能交给 Luna 自行定义。

### 7.5 路由升级不是失败惩罚

升级表示任务信息发生了变化，或初始分类不再适用。升级时应保留已有侦察和实现证据，缩小需要重新判断的部分，避免无意义地重做全部工作。

## 8. 并行 Agent 拆分原则

### 8.1 适合并行的工作

多个 Agent 可以并行处理互不写入同一决策面的工作，例如：

- Luna A 调查受影响文件和已有模式；
- Luna B 检查相关测试、链接和历史文档；
- Luna C 整理需求到页面/对象/验收标准的追踪表；
- Terra 在决策包确认后分别实现边界清楚的模块；
- Luna 对已完成的不同模块分别进行机械验证。

并行结果必须先汇总给一个协调者，再形成唯一的实现计划。多个 Agent 的意见不能自动拼成产品决定。

### 8.2 拆分的硬规则

- 每个并行 Agent 必须有单一目标和明确输出格式；
- 每个可写文件或产品决策面只能有一个 owner；
- 不允许多个 Agent 同时修改同一核心文档、同一共享对象或同一状态机；
- 并行 Agent 不能各自发明一套命名、状态或验收标准；
- 每个子任务必须说明它依赖哪些前置决定，以及完成后交给谁；
- 需要共享的上下文应通过结构化交接包传递，而不是依赖各自阅读完整聊天记录；
- 并行结果存在冲突时，立即由 Sol 处理，不由最后写入文件的 Agent 获胜；
- 初始拆分宜保持在少量、边界清楚的子任务内；拆得越细，不代表总质量越高。

### 8.3 好的拆分与不好的拆分

| 拆分方式 | 判断 |
|---|---|
| “调查 Timeline 相关文件”与“检查 Timeline 现有测试” | 好：读面不同，结果可合并 |
| “分别设计 Session 的定义”交给三个 Agent | 不好：产生多个产品真相 |
| “Terra 实现页面，Luna 检查链接和基础状态覆盖” | 好：职责分离，验证边界清楚 |
| “三个 Agent 同时改 README、Master PRD 和 Version PRD” | 不好：权威层级和决策所有权混乱 |
| “按模块拆分已经批准的独立实现” | 可以：前提是共享对象和边界已由 Sol 固定 |
| “把一个未定义的跨模块问题拆给多个 Agent 各自猜” | 禁止：应先回到决策阶段 |

### 8.4 并行交接包

每个子 Agent 至少收到：

- 任务目标与明确非目标；
- 必读文档和相关章节；
- 当前版本和允许修改范围；
- 已确认的产品决定；
- 输入、输出和验收标准；
- 不得擅自决定的事项；
- 交付格式、文件 owner 和回报对象。

每个子 Agent 至少返回：

- 已完成事项；
- 证据或文件位置；
- 未完成事项；
- 新发现的风险和歧义；
- 假设；
- 是否建议升级。

| 难以定位或跨模块 Bug | Sol 诊断方向 | Luna 调查，Terra 执行修复 | 任何数据、权限或产品语义风险 | 诊断结论、修复计划与审查结果 |
| 单元/集成/验收测试 | Terra 设计有意义的测试 | Luna 生成重复样例并执行基础检查 | 测试口径本身不清、风险接受标准不明 | 测试覆盖、失败分类和残余风险 |
| 批量迁移、命名和格式化 | Luna | Terra 处理例外，Sol 审查语义风险 | 共享对象、字段含义或历史数据被改变 | 变更清单和机械验证 |
| 跨模块重构 | Sol 定义边界 | Terra 主实现，Luna 检查引用/回归 | 公开行为改变、迁移或大量返工 | 重构计划、分段产出和审查结论 |
| 性能、可用性与成本优化 | Terra | Luna 测量和整理数据 | 需要架构取舍、牺牲隐私/可靠性或改变用户体验 | 基线、改动、效果和风险 |
| 文档索引、链接、格式 | Luna | Terra 处理需要理解语义的更新，Sol 审查产品决定 | 文档层级冲突或产品语义变化 | 文档变更和完整性检查 |
| 发布前检查与版本接受 | Sol | Luna 机械验证，Terra 修复 | 任一高风险项未解释或验收证据不足 | 发布决定或阻断清单 |

### 9.1 关于 V0.1 的特别规则

V0.1 的具体实现默认采用：

> Sol 确认范围与行为 → Terra 主实现 → Luna 机械验证 → Sol 按风险最终审查

V0.1 中“暂不实现”的 Master 能力仍然保留在 Master PRD 中，不得因为当前版本没有入口就删除或重新定义。任何为了实现方便而改变长期产品含义的做法，都必须回到 Sol 和产品文档。

## 11. 交接与证据要求

### 11.1 交接不能只说“已完成”

每次从一个模型角色交给另一个角色时，至少要说明：

- 已完成什么；
- 依据了哪份文档和哪条决定；
- 哪些地方是假设；
- 哪些地方没有覆盖；
- 运行了什么检查；
- 检查没有证明什么；
- 是否出现新的歧义、风险或范围变化；
- 下一角色必须做出的判断。

### 11.2 产品审查与机械验证的证据不同

- 机械证据可以证明某个链接存在、某个检查通过、某个清单被覆盖；
- 产品证据还必须说明行为符合使命、边界、用户流程和版本范围；
- 测试通过不能证明隐私授权正确；
- 页面能打开不能证明 Timeline、Echo 或 Ask My Life 的产品语义正确；
- AI 能生成回答不能证明回答有证据、没有越权或没有把推测伪装成事实。

## 12. 路由效果的持续测量

模型路由不是一次性拍板。LifeOS 每完成一批可比较的工作，就应记录实际效果，并据此调整路由，而不是凭印象争论哪个模型“感觉更强”。

### 12.1 每项任务建议记录的字段

| 字段 | 说明 |
|---|---|
| Task ID / 日期 | 便于回看同一任务和版本背景 |
| 任务类型 | 调查、决策、实现、验证、Bug、文档、同步等 |
| 五项指标 | Ambiguity、Scope、Risk、Reasoning、Repetition 的初始判断 |
| 计划角色 / 实际模型 | 计划用 Sol/Terra/Luna，以及实际调用的模型配置 |
| 阶段 | 侦察、决策、实现、验证、最终审查 |
| 首次通过 | 第一次提交是否达到验收标准 |
| 返工轮数 | 为达到同一目标所需的额外轮次 |
| 审查缺陷 | Reviewer 发现的语义、范围、质量或风险问题 |
| 升级/降级记录 | 发生了什么信号，路由是否及时调整 |
| 时间、Token、成本 | 环境可提供时记录；不能获得时标记未知 |
| 用户介入 | 是否需要补充决定、纠正误解或手动合并 |
| 结果 | 通过、延期、阻断、取消或重新定义 |

### 12.2 四个核心指标

1. **一次通过率**：首次提交即通过对应验收门槛的任务比例；
2. **返工率**：需要实质返工的任务比例，以及平均返工轮数；
3. **成本**：按任务类型统计的模型调用成本、Token 或其他可用资源指标；
4. **任务适配度**：每种任务类型使用某角色时的质量、速度、返工和审查缺陷表现。

可以额外记录：升级准确率、未发现缺陷、用户纠正次数、发布后回滚次数和隐私事件。隐私或原始记录损坏应视为阻断级事件，不得用平均成本抵消。

### 12.3 什么时候调整路由

- 一个任务类型连续出现低一次通过率或高返工率：提高默认角色或先增加 Sol 决策阶段；
- Luna 的机械工作一次通过率高且没有语义逃逸：可以扩大相同模式的 Luna 范围；
- Terra 在已明确需求下稳定完成：保持其为主力，不因个别复杂任务整体升级；
- Sol 经常被用于可机械验证的工作：拆出侦察和验证阶段，降低不必要成本；
- 成本下降但审查缺陷、用户纠正或返工上升：恢复更高质量的路由；
- 平台模型能力、上下文限制或可用名称变化：重新做小规模代表性任务验证。

路由策略的优化目标是“总交付质量、可解释性和成本的平衡”，不是单独追求最低调用成本或最少 Agent 数量。

### 12.4 变更记录

当路由规则发生有意义的改变时，应在 `LifeOS_Decision_Log.md` 记录：

- 原规则；
- 触发改变的任务样本和数据；
- 新规则；
- 预期改善；
- 复查时间或复查条件。

## 13. 文档权威层级与 Codex 启动清单

### 13.1 权威层级

1. Product Constitution：不可违背的使命、价值观与长期边界；
2. Master PRD：完整产品形态、对象关系和长期能力；
3. 当前 Version PRD：当前阶段允许实现的范围和验收标准；
4. 其他产品/设计文档：补充具体方案；
5. Model Routing and Codex Workflow：规定如何协作、分工和升级，不能改变产品语义；
6. Decision Log：解释历史决定、前提和待决问题；
7. 聊天记录、临时笔记和 Agent 推断：只能作为线索，不能单独作为权威需求。

如果“当前版本暂不实现”与 Master PRD 同时出现，不是冲突：Master 定义最终产品，Version PRD 定义当前裁剪。若出现真正冲突，停止执行并上报。

### 13.2 Codex 启动清单

每个非纯机械任务开始时，Codex 应按 [`Codex_Operating_Manual.md`](Codex_Operating_Manual.md) 的启动清单执行。本节只补充与模型路由直接相关的项目：

1. 按 Operating Manual 读取 README、Product Constitution、当前 Version PRD、相关 Master PRD 章节、Decision Log 和本文件；
2. 若任务涉及对象、状态或术语，补读 `CONTEXT.md`；
3. 用 Ambiguity、Scope、Risk、Reasoning、Repetition 五项指标写出简短路由判断；
4. 判断是否需要 Luna 侦察、Sol 决策、Terra 实现、Luna 验证和 Sol 最终审查；
5. 为每个并行 Agent 指定单一目标、owner、输入、输出和升级条件；
6. 任务中出现高歧义、高风险、范围扩大或产品取舍时立即升级到 Sol；
7. 记录未决问题、返工、升级和可复用的路由经验，并按 Operating Manual 完成最终汇报。

## 14. 最低合规标准

一次 LifeOS 协作只有在以下条件都满足时，才能被称为“按本工作流完成”：

- 任务范围和非目标明确；
- 选择模型角色的理由与五项指标相符；
- 需求缺口没有被执行 Agent 静默填补；
- 核心产品决定和实现工作有职责分离；
- 变更有对应的验收标准和证据；
- 高风险工作有 Sol 参与并完成最终审查；
- 并行工作有 owner、边界和汇总者；
- 未完成项、假设、阻断项和升级原因已记录；
- 发现新的长期决定时，已更新相应产品文档或 Decision Log。

这套工作流的最终目标不是让协作看起来复杂，而是让 LifeOS 在长期迭代中保持产品方向、生活记录真实性和用户信任。
