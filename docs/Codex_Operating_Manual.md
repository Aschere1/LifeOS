# Codex Operating Manual

> 文档类型：Codex / Agent 执行层标准作业程序（SOP）  
> 版本：v1.0  
> 状态：Draft / 可执行基线  
> 适用范围：LifeOS 的产品讨论、文档维护、设计、实现、测试、审查和交付任务  
> 不包含：具体业务实现代码、技术框架规定或某个功能的详细实现方案

---

## 0. 这份手册解决什么问题

LifeOS 不希望 Codex 变成“看到一句需求就直接写代码”的执行器。Codex 必须先理解产品长期方向、当前版本边界、任务授权和风险，再选择合适的模型与工作方式。

本手册的目标是让每个任务都遵循同一条可复核的路径：

> **读对文档 → 理解目标 → 确认范围 → 找到影响面 → 检查缺口 → 选择协作方式 → 制定最小计划 → 执行 → 验证 → 对照 PRD 验收 → 独立审查 → 汇报并落档**

本手册规定的是 Agent 如何工作，不是 LifeOS 应该具有什么产品功能。凡是涉及产品语义的判断，仍必须回到产品文档和用户确认。

## 0.1 规范用词

- **必须**：没有满足时，不得进入下一阶段。
- **应该**：默认遵守；偏离时要说明原因。
- **可以**：允许采用，不构成强制要求。
- **执行**：在已批准范围内调查、编辑、实现、测试或整理。
- **询问**：向用户或被明确授权的产品负责人请求决定，不是把问题推回给用户而不提供上下文。
- **上报**：提交事实、影响、选项和建议，等待决策后再继续。
- **原始数据**：用户输入、原始捕获、原始媒体和未经确认的生活记录，不得被 Agent 以推测替换。

## 1. 基本原则

### 1.1 文档先于实现

Codex 不得把聊天中的一句话、自己的常识或“实现起来最方便的方式”直接升级为产品需求。正式文档是产品行为的依据；聊天只能作为待整理的线索。

### 1.2 先确认授权，再决定动作

“请解释、请评审、请诊断、请规划”不自动授权修改文件；“请实现、请修复、请更新”通常授权在明确范围内进行本地变更，但仍不授权扩大产品范围、进行破坏性操作或替用户做未定义的产品选择。

### 1.3 发现歧义时停止猜测

Agent 的主动性应该用于调查、拆解、验证和推进已确认工作，而不是用于填补产品决策空白。重要歧义必须变成一个可回答的问题，并带上影响和候选方案。

### 1.4 保留真实生活记录

任何涉及 LifeOS 记录、时间线、媒体、人物、AI 或同步的工作，都必须优先保护：

- 原始输入可回看；
- 事实、用户表达和 AI 推测有明确区分；
- 默认隐私和最小授权不被扩大；
- 离线状态下不因网络不可用而丢失核心记录；
- 同步冲突不静默覆盖用户数据；
- 用户可以拒绝、修改、封存或删除系统建议。

### 1.5 只做完成目标所需的最小变更

任务完成不是“顺便把附近的一切都重构一遍”。额外发现可以记录、提出或单独拆任务，但不能未经批准混入当前交付。

## 2. 启动阅读顺序

### 2.1 固定的六步产品阅读顺序

每次接到 LifeOS 任务，先按以下顺序读取。即使任务看起来很小，也至少确认它没有触碰产品边界。

1. [`docs/README.md`](README.md)：确认文档入口、权威层级、当前版本和维护规则；
2. [`LifeOS_Product_Constitution.md`](LifeOS_Product_Constitution.md)：确认使命、永久原则和不可违背的边界；
3. 当前 Version PRD，例如 [`LifeOS_V0.1_PRD.md`](LifeOS_V0.1_PRD.md)：确认本次版本允许做什么、不做什么、怎样验收；
4. 与任务相关的 Master PRD 章节，例如 [`LifeOS_Master_PRD_v1.0.md`](LifeOS_Master_PRD_v1.0.md)：确认该能力在完整 LifeOS 中的长期语义和上下游关系；
5. [`LifeOS_Decision_Log.md`](LifeOS_Decision_Log.md)：查找历史取舍、先决条件、已知冲突和待决问题；
6. [`LifeOS_Model_Routing_and_Codex_Workflow.md`](LifeOS_Model_Routing_and_Codex_Workflow.md)：根据任务复杂度选择模型、拆分 Agent、安排验证和升级路径。

压缩表示为：**README → Product Constitution → 当前 Version PRD → 与任务相关的 Master PRD 章节 → Decision Log → Model Routing**。随后按本手册继续执行授权确认、范围控制、测试、验收、审查和汇报。

然后阅读本手册余下与当前任务相关的部分，并按本手册执行。这里的六步是“产品上下文和协作规则”的最小顺序；本手册本身是“如何执行”的入口。

### 2.2 术语和上下文的交叉查阅

如果任务涉及对象、状态或领域术语，必须同时查阅 [`../CONTEXT.md`](../CONTEXT.md)。它不是上述六步中的产品层级文档，而是跨任务使用的统一领域语言。若术语定义与新需求冲突，停止并提出文档更新问题。

### 2.3 可以缩短阅读的情况

只有以下工作可以缩短产品阅读：

- 纯只读搜索、文件清单、日志收集；
- 不改变语义的格式化、链接检查或重复校验；
- 已批准规则下的机械批量修改；
- 用户明确要求的文档排版修正，且不改变内容。

即使是上述任务，一旦发现共享对象、隐私、原始数据、同步、AI 权限、版本范围或产品语义问题，也必须回到完整阅读顺序。

## 3. 接到任务后的标准流程

每个非纯机械任务都应按以下阶段推进。阶段可以由一个 Agent 完成，也可以按 [模型路由与 Codex 协作工作流](LifeOS_Model_Routing_and_Codex_Workflow.md) 拆给多个角色；阶段顺序不能因为并行方便而被跳过。

### 阶段 0：确认任务授权

先判断用户请求属于哪一种：

| 请求类型 | 默认允许 | 默认不包含 |
|---|---|---|
| 回答、解释、评审、诊断、规划 | 阅读、调查、分析、报告 | 修改代码或文档、外部写入 |
| 创建、编辑、实现、修复 | 在目标项目内做明确范围的本地变更，运行相关的非破坏性检查 | 擅自扩展范围、破坏性操作、外部发送或产品拍板 |
| 迁移、删除、覆盖、批量重写 | 先确认精确目标、范围和可恢复性 | 对宽泛目录或未检查目标做递归破坏性操作 |
| 外部服务、分享、发布、购买 | 先报告即将发生的外部影响 | 把本地任务默认为外部授权 |

如果请求类型不清楚，先按较小授权处理并说明需要确认的部分。

### 阶段 1：用一句话重述目标

写出一条可验收的目标句，至少包含：

- 要解决的用户或产品问题；
- 要产生的结果；
- 目标位置或版本；
- 明确不做的内容。

目标句不能只是重复用户原话。例如“优化 Timeline”太宽；应进一步说明是修复某个已知回看问题、补充某个已确认状态，还是重新设计产品行为。若无法缩小含义，进入询问流程。

### 阶段 2：确认当前范围

根据当前 Version PRD 建立范围表：

| 项目 | 内容 |
|---|---|
| In scope | 本次必须完成的页面、流程、文档、测试或修复 |
| Out of scope | 明确不做或属于后续版本的内容 |
| Dependencies | 依赖的对象、模块、已有决定或外部条件 |
| Acceptance | 完成后必须能证明什么 |
| Approval boundary | 哪些动作需要用户或产品负责人确认 |

Master PRD 中存在但 Version PRD 明确暂缓的能力，不得因为实现顺手而提前加入当前范围。

### 阶段 3：识别受影响模块

先调查再改动，确认：

- 哪些页面、领域对象、状态和数据路径会受到影响；
- 哪些文档、测试、导航、同步或权限规则与之相关；
- 是否存在共享文件或其他 Agent 正在修改的 owner 区域；
- 现有行为、命名和验收约定是什么；
- 哪些影响是已确认事实，哪些只是待验证假设。

在此阶段可以让 Luna 做仓库侦察；调查结果要交给决策者或主执行者，不应被当成产品决定。

### 阶段 4：检查需求缺口和冲突

逐项检查：

1. Product Constitution 是否给出永久原则；
2. 当前 Version PRD 是否给出当前行为和范围；
3. 相关 Master PRD 章节是否定义长期语义；
4. Decision Log 是否存在历史取舍或待决项；
5. 文档之间是否存在冲突；
6. 继续执行是否需要创造一个新的产品行为。

如果仍然没有答案，必须停止相关语义工作，按照第 5 节上报或询问。不要以“先写出来再说”绕过缺口。

### 阶段 5：选择模型和 Agent 组合

根据五项指标选择角色：

- 歧义、跨模块范围、隐私/数据/同步风险或高难度推理升高：让 Sol 负责决策；
- 方案已定、范围清楚、需要真实实现：Terra 主导；
- 仓库调查、批量机械修改、基础验证和清单检查：Luna 主导。

具体路由、升级降级、并行拆分和 Reviewer 分离，遵循 [`LifeOS_Model_Routing_and_Codex_Workflow.md`](LifeOS_Model_Routing_and_Codex_Workflow.md)。本手册不复制那份文档的角色细节，只规定何时必须调用它。

### 阶段 6：制定最小可行执行计划

计划至少说明：

- 目标和非目标；
- 受影响区域；
- 先调查还是可以直接修改；
- 需要的模型角色和原因；
- 逐阶段产出；
- 验证方式；
- 可能的升级点；
- 哪些问题会阻断执行。

计划应足够小，使每一步都能被验证。不要先设计一个覆盖未来所有能力的大框架，再用当前任务为借口实现它。

### 阶段 7：按批准范围执行

执行中必须：

- 遵守已经确认的对象、状态、权限和用户流程；
- 保持修改集中、可回看、可撤回；
- 把临时假设显式列出；
- 发现新问题时停在边界处并升级，不让问题悄悄变成新需求；
- 不覆盖原始输入，不把 AI 建议直接当成事实；
- 不以测试通过为理由改变产品语义。

### 阶段 8：运行测试和基础验证

验证深度按风险匹配，至少覆盖第 10 节的要求。测试失败要分类：

- 实现缺陷；
- 环境或依赖问题；
- 测试本身过时；
- 需求或验收标准不完整；
- 发现了新的产品决策。

不能把最后三类伪装成普通实现缺陷并自行修正。

### 阶段 9：对照 PRD 验收

使用目标、范围、状态、异常和验收清单逐项核对：

- 当前 Version PRD 的每项要求是否有对应结果；
- Out of scope 是否真的没有被带入；
- Master PRD 的长期语义是否被保持；
- Constitution 的原则是否仍成立；
- 未实现项是否明确，而不是留在模糊状态。

### 阶段 10：Reviewer 独立审查

执行者不能把自己的“看起来完成”当成独立验收。根据风险安排：

- Luna：机械完整性、链接、引用、基础状态和重复模式检查；
- Terra 之外的上下文：普通实现的行为和测试复核；
- Sol：产品语义、跨模块行为、隐私、AI、同步、数据和发布前最终审查。

高风险任务必须把 Implementer 与 Reviewer 分开；发现 `Needs Decision` 时，回到 Lead，而不是由 Reviewer 直接改写产品规则。

### 阶段 11：结果汇报和文档落档

按第 13 节的标准格式汇报：做了什么、改了哪些区域、如何验证、还剩什么风险、是否发现需求缺口、是否需要更新 PRD 或 Decision Log。

如果形成了新的产品决策，必须先进入文档体系，再把它当作后续任务的依据。

## 4. 什么情况下可以直接执行

以下条件全部满足时，可以在用户已经授权的范围内直接执行，不必为每个本地、可逆的小动作再次询问：

- 目标、范围和非目标清楚；
- 当前 Version PRD 给出了预期行为或用户明确给出了验收标准；
- 相关 Master PRD 语义没有冲突；
- 不需要创造新的产品行为；
- 影响范围和 owner 清楚；
- 风险可回滚，不涉及未经确认的删除、覆盖、授权或外部写入；
- 不会扩大隐私、AI 读取、媒体、分享或同步权限；
- 可以通过明确的测试或检查判断结果；
- 任务是实现、修复、整理或验证，而不是替用户做未表达的取舍。

典型可直接执行的工作包括：

- 按已确认的页面和状态清单实现局部功能；
- 修复有稳定复现步骤且预期行为已明确的普通缺陷；
- 按明确模式批量更新文案、链接、格式或命名；
- 调查仓库引用、生成影响清单和测试矩阵；
- 运行非破坏性测试、静态检查和文档链接检查；
- 补齐已定义验收项对应的基础测试。

“可以直接执行”只代表可以开始已授权动作，不代表可以自行扩大范围或批准最终产品行为。

## 5. 什么情况下必须停下来询问或上报

出现以下任一情况，必须停止受影响的部分，先询问用户或交给 Sol/产品负责人处理：

### 5.1 产品语义不确定

- 需求存在两个或更多合理解释；
- 新功能需要定义对象、状态、统计口径或用户可见行为；
- 不知道某个功能属于当前版本还是未来版本；
- 需要决定“什么应该被记录、归档、提醒、回响或分析”；
- 需要把系统推断写成生活事实。

### 5.2 文档冲突或缺失

- Product Constitution、Master PRD、Version PRD 或 Decision Log 互相冲突；
- 当前版本没有定义但实现必须做选择；
- 聊天内容与正式文档不一致；
- 术语含义发生漂移；
- 验收标准不足以区分多个方案。

### 5.3 高风险数据或用户信任问题

- 可能删除、覆盖、合并、重写或丢失原始记录；
- 需要改变默认隐私、Space、分享或 AI 读取权限；
- 需要处理人物、敏感地点、媒体或私密时期；
- 需要定义离线记录、同步冲突、恢复或多设备一致性；
- AI 可能把推断混入事实，或外部 AI 可能看到未授权数据；
- 失败会长期污染用户的生活档案。

### 5.4 范围、授权或外部影响不清

- 需要修改用户没有指定的文件、项目或目录；
- 需要大规模重构、迁移、删除或覆盖；
- 需要访问外部服务、发送消息、发布内容、购买资源或改变外部状态；
- 需要新的凭据、权限、依赖或不可逆环境变化；
- 发现“顺手优化”会显著增加改动量或改变公共行为。

### 5.5 质量证据不足

- 测试失败但无法判断是实现错还是需求错；
- Reviewer 与 Implementer 对预期行为有实质分歧；
- 连续两次普通返工仍无法达到验收标准；
- 机械检查通过，但核心用户体验、隐私或产品语义无法证明；
- 环境阻断了关键验证，继续汇报“已完成”会造成误导。

### 5.6 询问的正确格式

不要只问“怎么办”。应提交：

1. 已确认的事实；
2. 已查阅的文档和相关章节；
3. 精确的缺口或冲突；
4. 受影响的页面、对象、数据和版本；
5. 两到三个可行选项及取舍；
6. 默认建议及其理由；
7. 用户只需确认的具体问题；
8. 在等待决定期间可以继续的安全工作。

## 6. 需求冲突处理规则

### 6.1 权威层级

产品语义冲突按以下顺序处理：

> **Product Constitution > Master PRD > 当前 Version PRD > 其他设计文档**

聊天记录、临时笔记和 Agent 推断不能单独覆盖正式文档。`Decision Log` 是关键决策的解释和历史记录；它帮助理解原因，但不替代上面的产品定义。

模型路由文档和本 Operating Manual 属于协作层：它们规定谁来调查、谁来实现、如何审查和什么时候停，不得改变产品语义。

### 6.2 Version PRD 暂缓 Master 能力不算冲突

以下关系是合法的：

- Master PRD：LifeOS 长期需要 Echo；
- 当前 Version PRD：本版本暂不实现 Echo。

版本 PRD 可以裁剪当前交付范围，但不能重新定义 Echo 的长期含义，也不能用临时实现把未来能力变得不可能。

### 6.3 冲突处理步骤

1. 停止受冲突影响的语义修改；
2. 保存当前调查结果，不丢弃已有证据；
3. 标出冲突所在的文档、章节和具体句子；
4. 判断是不是“当前暂不实现”，而不是实际冲突；
5. 若仍冲突，向 Sol/产品负责人或用户上报；
6. 获得决定后，先更新对应 PRD、CONTEXT 或 Decision Log；
7. 再恢复实现，并在汇报中链接新决定。

禁止以“下位文档更具体”“代码已经写了”或“这样最省事”为理由静默解决冲突。

## 7. 禁止事项

### 7.1 禁止擅自新增产品行为

不得自行增加未定义的：

- 页面入口、状态、自动提醒、评分、等级、Streak 或惩罚；
- 对生活记录的分类、合并、归档、回响或推断规则；
- 人物关系、地点、媒体和 AI 的可见性或读取权限；
- 同步冲突处理、删除恢复或数据迁移行为；
- 当前版本以外的长期系统能力。

### 7.2 禁止为了实现方便修改产品语义

不得因为数据结构、组件复用、测试、性能或实现成本方便而：

- 把 Session 当成 Task，或改变已有对象边界；
- 把用户没有写出的内容补成事实；
- 让 AI 建议直接成为正式记录；
- 用一个模糊状态隐藏失败、未知或冲突；
- 用分值、连续签到或惩罚替代真实成长和回顾；
- 把当前版本临时方案说成最终产品定义。

### 7.3 禁止跳过原始数据、隐私和 AI 边界

不得：

- 覆盖原始 Capture、用户原话或原始媒体；
- 默认扩大外部 AI 的输入范围；
- 把存在的数据等同于已授权 AI 读取；
- 在没有证据、标注和用户控制的情况下生成长期人格结论；
- 在离线或同步失败时静默丢弃记录；
- 用“用户以后可以恢复”掩盖当前不可逆的数据损失。

### 7.4 禁止顺手扩大范围

发现与当前任务无关的改进时：

- 记录发现和影响；
- 如果可能阻断当前工作，单独上报；
- 如果不阻断，创建后续建议或任务；
- 不把它混入当前交付，除非用户明确批准。

### 7.5 禁止伪造完成或证据

不得：

- 没有运行检查却声称测试通过；
- 只检查了机械完整性却声称产品验收通过；
- 把环境阻断隐瞒为实现完成；
- 把假设写成已确认需求；
- 把 Reviewer 的意见省略在最终汇报中；
- 把未解决的 PRD 缺口留在代码或聊天里。

## 8. 任务拆分与并行规则

### 8.1 默认先串行后并行

以下部分必须串行：

1. 读取产品文档与确认授权；
2. 识别需求缺口和冲突；
3. 定义跨模块边界、对象语义和验收标准；
4. 需要用户或 Sol 决定的产品取舍；
5. 最终汇总、PRD 对照验收和发布判断。

以下部分在边界清楚后可以并行：

- 不同区域的仓库侦察；
- 文档、引用和测试清单收集；
- 独立模块的已批准实现；
- 不同模块的机械验证；
- 日志、链接、格式和重复模式检查。

### 8.2 可以并行的必要条件

并行前必须确认：

- 每个子任务有单一目标、owner 和输出格式；
- 子任务不需要各自做同一个产品决定；
- 不会同时修改同一个核心文件、共享对象或状态定义；
- 共享输入已经固定，或只读调查结果明确标注为事实/假设；
- 有一个协调者负责合并和处理冲突；
- 每个 Agent 知道什么时候必须停止并升级。

### 8.3 禁止并行的情况

不得并行：

- 多个 Agent 同时设计同一个核心对象的含义；
- 多个 Agent 同时编辑同一份产品宪法、Master PRD、Version PRD 或 Decision Log；
- 需求未确认时让多个 Agent 各自猜一套实现；
- 共享数据迁移、同步冲突或权限修改没有唯一 owner；
- 审查者与实现者共享同一份未完成判断，却把结果称为独立审查。

### 8.4 并行交接包

每个子任务应收到：任务目标、非目标、相关文档、批准决定、修改边界、验收标准、禁止事项、owner、回报对象和升级条件。

每个子任务应返回：完成项、文件/证据位置、未完成项、假设、失败项、新风险、需求缺口和是否建议升级。

协调者必须整理成一个唯一的合并结论。若结果冲突，交给 Sol 或用户决策，不能按最后写入顺序解决。

## 9. 变更范围控制与避免过度工程

### 9.1 变更前的四个问题

开始修改前，回答：

1. 这项变更直接对应哪个目标或验收项？
2. 不做它会阻断什么？
3. 它是否改变公共行为、对象语义、权限或数据生命周期？
4. 有没有更小、更可逆、同样满足目标的变更？

如果不能回答第一个问题，通常不应加入当前任务。

### 9.2 最小可行变更原则

- 优先修复当前问题，不提前搭建未使用的通用平台；
- 优先复用已存在且语义一致的模式，不为了抽象而抽象；
- 只为当前验收需要增加状态和边界；
- 将未来能力保留在产品语义和扩展点记录中，不要求当前版本全部实现；
- 把性能、可配置性和自动化投入与真实风险和使用证据匹配；
- 大重构应拆成可独立验收的阶段，并有明确收益。

### 9.3 “顺手优化”处理方式

若发现邻近改进：

- 属于完成当前验收所必需：纳入计划并说明原因；
- 属于降低当前风险所必需：在本次任务中做最小修正，并记录范围；
- 不影响当前交付：列为后续任务，不混入当前变更；
- 可能改变产品行为：先上报，不直接优化。

## 10. 测试与验收要求

测试不是最后一条命令，而是从任务计划开始就确定的证据。每项交付都要根据风险选择适当深度，至少考虑以下方面。

### 10.1 功能正确

- 主流程符合当前 Version PRD；
- 关键输入、输出和状态变化符合已确认定义；
- 页面入口、返回、刷新和重新进入行为没有破坏；
- 结果可以被用户理解，重要数据可以回看；
- 已实现项与验收标准一一对应。

### 10.2 异常和边界状态

至少检查与任务相关的：

- 空数据、首次使用、未知内容和部分完成；
- 重复点击、重复提交、取消、返回和重新打开；
- 无效输入、缺失字段、超时、失败和重试；
- 时间重叠、跨日、时区或时间修正；
- 并发修改、冲突、网络中断和恢复；
- 权限不足、私密内容和用户拒绝建议。

不应只验证“成功路径能跑通”。

### 10.3 数据安全与原始记录

- 原始输入、原始媒体和用户表达仍可追溯；
- AI 建议有来源、状态和人工控制；
- 删除、合并、导入、导出和恢复行为符合用户预期；
- 没有新增未授权的数据收集或共享；
- 失败不会静默丢失或覆盖生活记录；
- 记录和推断在展示中保持区分。

### 10.4 离线和同步产品行为

只要任务触及多设备、Local-first、网络或数据写入，就必须验证产品行为：

- 无网络时核心记录是否仍可创建、查看和继续编辑；
- 同步失败是否可见、可重试且不丢数据；
- 同一记录在多个设备被修改时是否保留冲突证据；
- 合并或覆盖是否需要用户确认；
- 重复同步、乱序同步和恢复后重试是否会重复或污染记录；
- 用户是否知道当前数据是本地、已同步、待同步还是冲突状态。

### 10.5 PRD 一致性

验收者必须对照：

- Constitution 的使命和边界；
- Master PRD 的相关长期语义；
- 当前 Version PRD 的范围、状态、异常和验收；
- Decision Log 的历史取舍；
- `CONTEXT.md` 的对象和术语定义。

如果测试结果与 PRD 不一致，优先报告冲突，不要默认测试或 PRD 哪个应该被改。

### 10.6 验收证据分层

- **机械证据**：测试、lint、类型检查、链接检查、文件清单、日志和复现步骤；
- **行为证据**：主流程、异常状态、权限、离线/同步和用户可见结果；
- **产品证据**：符合使命、领域语义、版本范围和历史决策；
- **风险证据**：没有引入数据丢失、越权读取、不可逆破坏或未批准的范围扩张。

低风险任务可能只需机械证据；核心 LifeOS 功能不能只凭机械证据通过。

## 11. Reviewer 审查要求

### 11.1 Reviewer 必须回答的问题

- 任务目标是否真的完成，而不是只完成了一部分代码工作；
- 是否修改了未授权区域；
- 是否存在隐藏假设、未处理异常或错误的空白状态；
- 是否违反产品宪法、Master PRD、Version PRD 或历史决定；
- 是否改变了原始数据、隐私、AI、媒体或同步边界；
- 测试证据是否足够，是否存在“测试通过但需求不对”；
- 是否应更新 PRD、CONTEXT 或 Decision Log；
- 是否可以安全交付，还是需要返工、决策或阻断。

### 11.2 审查结果格式

Reviewer 必须输出以下四种状态之一：

- **Pass**：目标、范围、证据和风险均达到要求；
- **Changes Requested**：产品方向明确，只需进行具体返工；
- **Needs Decision**：存在产品取舍、文档冲突或权限/风险决定；
- **Blocked**：环境、依赖、权限或缺失资料使可靠判断无法完成。

审查意见应指向具体需求、文件、流程或证据，不用模糊的“感觉不太对”。Reviewer 不得静默替换产品规则来让结果通过。

## 12. Definition of Done

LifeOS 任务只有在以下条件全部满足时才算完成：

### 12.1 目标与范围

- [ ] 目标已经被明确重述；
- [ ] In scope、Out of scope 和授权边界已经确认；
- [ ] 没有把未来 Master 能力擅自提前；
- [ ] 没有未经批准的顺手优化或范围扩张。

### 12.2 产品一致性

- [ ] 已按启动顺序阅读相关产品文档；
- [ ] 使用了 `CONTEXT.md` 中的统一术语；
- [ ] 符合 Product Constitution；
- [ ] 符合相关 Master PRD 长期语义；
- [ ] 符合当前 Version PRD 的范围和验收；
- [ ] 历史取舍和待决问题已被正确处理。

### 12.3 实现与验证

- [ ] 主要目标已经实现或明确说明无法完成的部分；
- [ ] 主流程和相关异常状态已验证；
- [ ] 数据安全、原始记录、隐私和 AI 边界已检查；
- [ ] 相关离线/同步产品行为已检查；
- [ ] 测试结果和环境限制已真实记录；
- [ ] Reviewer 已独立完成与风险匹配的审查；
- [ ] 最终状态为 `Pass`，或用户明确接受剩余风险。

### 12.4 文档与交接

- [ ] 未解决风险、假设和阻断项已列出；
- [ ] 新产品决策已写入对应 PRD、CONTEXT 或 Decision Log；
- [ ] 模型路由、返工和升级经验已按需要记录；
- [ ] 结果汇报包含下一步或无需下一步的明确结论；
- [ ] 后续 Agent 可以仅凭交接信息理解当前状态。

“代码可以运行”或“测试没有报错”本身不等于 Definition of Done。

## 13. 标准结果汇报格式

每次任务结束时，按以下顺序汇报，避免只给出一句“完成了”：

### 13.1 做了什么

- 用一到三句话说明完成的用户目标和实际结果；
- 说明哪些内容明确没有做，以及原因。

### 13.2 改了哪些区域

- 文件、模块、页面、文档或配置区域；
- 变更是新增、修改、删除、迁移还是只读验证；
- 如果有多个 Agent，说明各自负责的区域和交接结果。

### 13.3 测试和验收结果

- 运行了哪些测试、检查或手动流程；
- 哪些通过、哪些失败、哪些未覆盖；
- 结果是机械验证、行为验证还是产品审查；
- 是否完成 PRD 对照验收；
- Reviewer 状态：Pass / Changes Requested / Needs Decision / Blocked。

### 13.4 未解决风险

- 未解决的缺陷、环境问题、假设和数据风险；
- 风险影响、发生条件和建议下一步；
- 是否需要用户、Sol 或产品负责人决定。

### 13.5 PRD 缺口和文档更新

明确回答：

- 是否发现 Product Constitution、Master PRD、Version PRD 或 Decision Log 的缺口/冲突；
- 是否已更新 PRD、`CONTEXT.md` 或 Decision Log；
- 若尚未更新，谁需要决定、应该更新哪份文档；
- 是否形成新的模型路由或协作经验。

### 13.6 推荐的结尾句

> 结论：本任务已达到 / 尚未达到 Definition of Done。当前状态为 **Pass / Changes Requested / Needs Decision / Blocked**。剩余工作是……；如果形成了产品决定，需要先更新……。

## 14. 新的产品决策必须进入文档体系

任务中一旦出现新的产品决策，不得只留在代码注释、实现细节、Agent 交接或聊天记录中。必须根据决策性质落到正确位置：

| 决策内容 | 应更新的位置 |
|---|---|
| 改变 LifeOS 使命、价值观或永久边界 | Product Constitution，并在 Decision Log 记录背景 |
| 改变长期系统、对象、闭环或能力定义 | Master PRD，并在 Decision Log 记录取舍 |
| 改变当前版本范围、页面、流程、状态或验收 | 当前 Version PRD，并在 Decision Log 记录原因 |
| 改变对象术语或边界 | `CONTEXT.md`，必要时同步 Master/Version PRD |
| 解释为何选择某方案、放弃某方案或暂缓某能力 | Decision Log |
| 改变模型角色、升级阈值、并行规则或审查流程 | Model Routing 或本手册，并在 Decision Log 记录依据 |
| 只是实现细节且不改变产品语义 | 工程文档或代码；仍需在汇报中说明 |

更新文档后，必须检查交叉链接、版本范围和“暂不实现”表述，避免把一个局部决定误写成终局产品定义。

## 15. 与模型路由文档的关系

### 15.1 两份文档各自负责什么

| 文档 | 负责的问题 | 不负责的问题 |
|---|---|---|
| `LifeOS_Model_Routing_and_Codex_Workflow.md` | Sol/Terra/Luna 的角色、五项路由指标、自动升级/降级、并行 Agent、Reviewer/Implementer 分离、路由效果度量 | 具体业务实现、每次任务的完整 SOP |
| `Codex_Operating_Manual.md`（本文） | 每次接任务的阅读顺序、授权判断、执行阶段、停问条件、范围控制、测试、DoD 和结果汇报 | 重新定义模型能力、产品语义或具体业务代码 |

### 15.2 引用方式

本手册在三个节点引用模型路由文档：

1. 阶段 5：选择模型和 Agent 组合时，读取五项指标和默认路由表；
2. 阶段 8–11：安排机械验证、Implementer/Reviewer 分离和 Sol 最终审查时，遵循其角色规则；
3. 阶段 14：如果任务形成路由规则的新证据，按其度量方式记录一次通过率、返工率、成本和任务适配度。

反过来，模型路由文档应把本手册视为每次任务的执行入口。若两份协作文档出现流程措辞差异，以当前任务明确的授权、产品文档和用户决定为准；不得利用协作层差异改变产品语义。

### 15.3 最小协作闭环

在需要多模型或多 Agent 时，默认闭环为：

> **Operating Manual 确认任务 → Luna 侦察 → Sol 关键决策 → Terra 主实现 → Luna 机械验证 → Sol 最终审查 → Operating Manual 汇报与落档**

小型、低风险、边界明确的任务可以缩短闭环，但不能跳过需求缺口检查、基本验证和真实汇报。

## 16. 快速执行清单

当任务很短时，可以用下面的压缩版，但它仍然代表完整 SOP 的最低要求：

1. 读 README、Product Constitution、当前 Version PRD、相关 Master 章节、Decision Log、Model Routing；
2. 用一句话写目标、范围和非目标；
3. 找受影响模块，并确认没有需求缺口；
4. 判断可以直接执行，还是必须询问；
5. 按五项指标选择 Sol、Terra、Luna 和 Reviewer；
6. 制定最小执行计划，明确异常、数据和隐私检查；
7. 在批准范围内实现或整理；
8. 运行功能、异常、数据安全、离线/同步和 PRD 一致性验证；
9. 完成独立 Reviewer 审查；
10. 用标准格式汇报，并将新的产品决定写入文档。

如果无法完成第 3 或第 4 步，不得直接进入实现。先调查、上报或询问，正是这份手册存在的原因。

## 17. 最终承诺

LifeOS 的工程效率不是“越快写出代码越好”，而是用尽可能少的返工，把正确的产品行为稳定地交付出来。Codex 的主动性应服务于理解、证据、边界和交付质量：

> **先理解一个人的生活系统，再改变它；先保护真实记录，再增加智能；先确认产品决定，再开始实现。**
